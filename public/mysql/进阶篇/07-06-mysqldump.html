7.2.5mysqldump

逻辑备份工具。产物是一个纯文本 .sql，内容是「建表语句 + 插入语句」，重放一遍就能还原数据。中小库备份的默认答案。

进阶篇 · 7.2 常用客户端工具 更新：2026-11-25 环境：MySQL 8.0

一屏速记合上笔记，这 5 条要能自己说出来

  1. 备份的是 database，不是整个 MySQL 安装。备几个由写法决定：db_name 备一个、-B db1 db2 备几个、-A 备全部。
  2. 单给 db_name 时，导出文件里既没有 CREATE DATABASE 也没有 USE，目标库必须事先存在；-B / -A 才带。
  3. -A 才是「整个实例」，它连 mysql 系统库一起导，账号和授权也在里面——这和 mysqlpump 默认不导账号正好相反。
  4. 存储过程、触发器、定时事件默认都不导，必须显式加 --routines --triggers --events，否则恢复时业务逻辑静默丢失。
  5. 线上库必加 --single-transaction（InnoDB 一致性快照，不锁表）；导到别的实例常加 --set-gtid-purged=OFF，否则导入报 GTID 冲突。

1. 一条命令拆成四段

语法mysqldump [options] db_name [tables]
mysqldump [options] --databases/-B db1 [db2 db3...]
mysqldump [options] --all-databases/-A

2. 备份粒度：database，不是整个 MySQL

这是最容易搞混的一点：它备份的永远是 database（库/模式），不是整个 MySQL 安装。具体备几个库，由参数决定。

为什么第一档没有 CREATE DATABASE

单个 db_name 只导出「库里有什么」，不导出「建这个库」这个动作。所以恢复命令里必须写目标库：
mysql -uroot -p itcast < dump.sql　否则报 ERROR 1046 (3D000): No database selected。
反过来说，正因为 -B/-A 自带建库语句，才有 -n, --no-create-db 这个开关去关掉它。

3. 能力边界：-A 也不等于整个 MySQL

「整个 MySQL 软件」这个说法要拆开看。逻辑备份只搬数据，不搬软件。哪怕加了 -A：

最容易踩：账号没备走

账号和权限存在 mysql 系统库里。mysqldump -uroot -p itcast 只导业务库，账号根本不进文件——恢复到新实例后表都在、应用连不上。

-A 能带上，因为它是连 mysql 库一起导的，账号以 INSERT INTO mysql.user 的形式落进文件。但这引出另一个坑：跨版本恢复（5.7 → 8.0）时 user 表结构变了，带密码哈希的 INSERT 很容易失败。

更稳的做法是把账号导成语句，而不是表数据：

-- 生成一份 grant 脚本，再在目标库执行
SELECT CONCAT('SHOW GRANTS FOR ''', user, '''@''', host, ''';')
FROM mysql.user;

真要「整机级」备份，方向不是加参数，而是换手段：物理备份（XtraBackup / 停机拷数据目录）、或 MySQL Shell 的 util.dumpInstance()。

4. 选项与实战

连接选项

选项全称说明
-u--user-name指定用户名
-p--password[=name]指定密码；-p 后不加空格，直接跟密码，或留空等提示输入
-h--host-name指定服务器 IP 或域名
-P--port=#端口（大写 P 是端口，小写 p 是密码）

输出选项

这一组里只有 -T 需要传值——它后面跟的是一个目录路径，其余全是纯开关（加了就生效，不加就关）。忘记写目录会直接报语法错误。

选项说明
--add-drop-database建库前加 DROP DATABASE，覆盖式还原
--add-drop-table建表前加 DROP TABLE，默认开启，关闭用 --skip-add-drop-table
-n / --no-create-db不包含建库语句
-t / --no-create-info不包含表结构，只导数据
-d / --no-data不包含数据，只导结构
-T / --tab=目录 必须跟一个目录路径，不能只写 -T。生成 表名.sql（建表）+ 表名.txt（数据，默认 TAB 分隔），分隔符可用 --fields-terminated-by 改

同一个限制：secure_file_priv 这个「信任目录」

-T 的文件是服务端写的，写到哪由 secure_file_priv 决定。路径不在它允许的目录里，不管目录存不存在、权限给没给，一律报 1290。这个变量同时管着 LOAD DATA、SELECT ... INTO OUTFILE、LOAD_FILE()，所以备份和恢复两侧都撞它。

sql-- 第一步永远是查值
SHOW VARIABLES LIKE 'secure_file_priv';

-- 想临时改？改不动：它是只读变量
SET GLOBAL secure_file_priv = '/tmp/';
-- ERROR 1238 (HY000): Variable 'secure_file_priv' is a read only variable
报错真实原因怎么解
ERROR 1290 (HY000)
The MySQL server is running with the --secure-file-priv option…		 路径不在信任目录内，或变量值是 NULL 把文件挪进该目录；NULL 只能改配置
ERROR 1227 (42000)
Access denied; you need the FILE privilege(s)…		 账号缺少 FILE 权限。路径对也不行 GRANT FILE ON *.* TO 'user'@'host';
ERROR 1238 (HY000)
Variable 'secure_file_priv' is a read only variable		 试图用 SET 改它，SET PERSIST 同样无效 改 my.cnf / my.ini 后重启
ERROR 13 (HY000)
Can't create/write to file… (Errcode: 13)		 路径合规，但 mysqld 这个系统用户没权限；或被 AppArmor / SELinux 挡住 给目录加属主与权限，查安全策略
要改这个值，得动配置并重启

Linux：/etc/my.cnf 或 /etc/mysql/my.cnf 的 [mysqld] 段加 secure_file_priv=/srv/mysql-files；Windows：C:\ProgramData\MySQL\MySQL Server 8.0\my.ini 里改 secure-file-priv。
改完还有两件事：目录要自己建（服务器不会替你创建，子目录不存在也报 1290），属主要给 mysql（chown mysql:mysql），然后重启服务。Ubuntu / RHEL 上还要确认 AppArmor 或 SELinux 放行这个新目录，否则报的是 Errcode: 13 而不是 1290。

两个方向各有一条逃生门，但不该当成常规做法

备份侧：别用 -T，直接 mysqldump … > dump.sql。这样文件是客户端写的，压根不经过 secure_file_priv。
恢复侧：mysqlimport --local，文件从客户端读，同理绕开。
绕开的是安全检查，不是问题本身。生产环境该做的是把交换目录配好、权限收紧，而不是关掉这道闸。

shell# 备份单个库（最常用）
mysqldump -uroot -p123456 --single-transaction --default-character-set=utf8mb4 \
  --routines --triggers --events -B itcast > itcast_20261125.sql

# 只备结构，给同事建表用
mysqldump -uroot -p123456 -d itcast > itcast_schema.sql

# 整实例：连 mysql 系统库一起导，账号权限随库走
mysqldump -uroot -p123456 -A --single-transaction --set-gtid-purged=OFF > all.sql

# -T：结构和数据分别落成两个文件，目录必须写在 secure_file_priv 里
mysqldump -uroot -p123456 itcast emp -T /var/lib/mysql-files/

# 恢复（单库备份必须指明目标库）
mysql -uroot -p123456 itcast < itcast_20261125.sql
课程没讲、但生产必备的三个参数

--single-transaction：InnoDB 下开一致性快照，备份全程不锁表，线上库必须加。
--routines --triggers --events：存储过程、触发器、定时事件默认不导，不加就静默丢失，恢复时才发现业务逻辑没了。
--set-gtid-purged=OFF：导出的文件不想把 GTID 信息带过去（比如导到测试库）时用，否则导入报 GTID 冲突。

mysqldump 现在还值得学吗

值得。它至今仍在维护，是中小库逻辑备份的默认答案；并行版 mysqlpump（8.0.34 弃用、8.4 已移除）已经退场，官方给大库的替代是 MySQL Shell 的 util.dumpSchemas() / util.dumpInstance()。
好消息：-B/-A/-d/-t/-n/-T 这套选项在 mysqldump、mysqlpump、MySQL Shell 里含义基本一致，学一遍能迁移过去。

自测三问先自己答一遍，再点开对答案

Q1mysqldump itcast > a.sql，在空实例上 mysql -uroot -p < a.sql 报 No database selected，为什么？

单库写法既不带 CREATE DATABASE 也不带 USE，脚本里的 CREATE TABLE 没有落点。要么先建库并指定（mysql -uroot -p itcast < a.sql），要么备份时改用 -B itcast。

Q2恢复完整库后业务报「存储过程不存在」，是哪一步漏了？

--routines --triggers --events 默认全都不导，不加就静默丢失，恢复时才发现。备份命令里补上这三项，重新备一份。

Q3用 -A 备份的文件导到另一台机器，报 SET @@GLOBAL.GTID_PURGED 相关错误，怎么解？

文件头把源库的 GTID 集合一起带过去了，目标实例的 gtid_executed 非空就冲突。备份时加 --set-gtid-purged=OFF；如果文件已经生成，导入前把那几行注释掉或手动清空。

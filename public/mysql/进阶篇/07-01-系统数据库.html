7.1系统数据库

装完就有四个库。它们不是「四个普通数据库」，而是四层不同的东西：一层存真相，一层做翻译，一层记运行时，一层把前两层包成人话。分不清就会做两件错事——备份时把系统库当业务库，或者出问题时不知道去哪查。

进阶篇 · 7.1 更新：2026-11-25 环境：MySQL 8.0

一屏速记合上笔记，这 5 条要能自己说出来

  1. 四个库不是平级：mysql 是账本（账号、权限、复制位点、统计），information_schema 是元数据视图，performance_schema 是运行时计数器，sys 只是前两者的易读外衣——sys 依赖前两者，前两者互不依赖。
  2. mysql 库 37 张可见表，分成「可以改的账本表」和「别手改的状态表」两类；另有约 30 张数据字典隐藏表，直接 SELECT 会报 ERROR 3554。
  3. 8.0 里 5.7 的 mysql.event、mysql.proc 已不存在（搬进了数据字典），但复制表仍叫 slave_master_info 这些旧名，没跟着 SOURCE / REPLICA 术语改名。
  4. 时区 5 张表默认是空的，没导时区数据前 CONVERT_TZ() 返回 NULL；information_schema.TABLES.TABLE_ROWS 是估算值，还被 information_schema_stats_expiry（默认 86400 秒）缓存。
  5. 查之前先分清「元数据还是运行时」：结构 / 权限 / 统计去 information_schema，计数器与等待事件去 performance_schema，想要人话查 sys。

1. 四个库不是平级

库存什么落盘能不能写备份要吗
mysql 账号与权限、复制位点、持久化统计、时区、帮助文本、日志表 是，全在 mysql.ibd 通过 ALTER USER / GRANT 间接改 要
information_schema 库、表、列、索引、约束、视图、触发器、存储过程、存储引擎 否，数据来自数据字典 不能，INSERT 直接报错 不要
performance_schema 运行时事件：SQL 耗时、锁等待、IO、内存分配 否，全在内存 只能改 setup_* 配置表 不要
sys 面向 DBA 的诊断视图 只有 sys_config 一张表 只能改 sys_config 不要
一句话记住边界

业务数据在你自己建的库里；账号和权限在 mysql 库。所以「只备份业务库」等于不备份账号——这条在 mysqldump 的粒度那一节已经踩过一次，这里是从库的角度解释原因。

2. mysql 库：37 张表，但有两类东西

课程里说「mysql 库存时区、主从、用户、权限」，这只是概括。8.0 的 mysql 库实际有 37 张可见的系统表，按用途能分成七组：

8.0 的坑：37 张只是「看得见的」

MySQL 8.0 把元数据搬进了数据字典，这些表（mysql.tables、mysql.columns、mysql.indexes、mysql.schemata 等约 30 张）被标记为隐藏：

-- 37 行，看不到 tables / columns / indexes 这些
SHOW TABLES FROM mysql;

-- 直接从库里查，被拒
SELECT * FROM mysql.tables;
-- ERROR 3554 (HY000): Access to data dictionary table 'mysql.tables' is rejected.

想看元数据只能走 information_schema：SELECT * FROM information_schema.tables。另外 5.7 里的 mysql.event、mysql.proc 在 8.0 已经不存在，对应内容进了数据字典的 events 和 routines。网上大量「查 mysql.proc 看存储过程」的脚本，在 8.0 上会直接报 1146。

2.1 权限表：账号存在哪

「用户」不是一串字符，是 User@Host 二元组。'root'@'localhost' 和 'root'@'%' 是两个完全不同的账号，权限互不相干。权限按作用范围分层存放，越往下越具体：

表一行代表什么时候会查它
user一个账号：认证插件、密码哈希、全局权限、锁定状态确认某账号能不能连、插件是不是 caching_sha2_password
db「某账号在某库上」的权限账号能连进来、却报 SELECT command denied
tables_priv表级权限只授了单表权限，排查为什么读别的表失败
columns_priv列级权限隐藏手机号、身份证列这类需求
global_grants动态全局权限（8.0 新增）SHOW GRANTS 里出现看不懂的 _ADMIN 权限
role_edges角色授予关系用角色管权限，查谁通过角色拿到了什么
password_history历史密码哈希启用了密码复用策略，禁止改回旧密码
 
sql-- 看有哪些账号、用什么认证插件、是否被锁
SELECT user, host, plugin, account_locked FROM mysql.user;

-- 别读表拼权限，用 SHOW GRANTS，它会把多层权限合并后展示
SHOW GRANTS FOR 'itcast'@'%';

-- 手工改过权限表（不推荐）之后必须刷缓存
FLUSH PRIVILEGES;
三个容易踩的点

1. 内置账号别删。mysql.sys 是 sys 库所有视图的 DEFINER，mysql.session 供插件内部连接，mysql.infoschema 读 information_schema。它们的 account_locked 都是 Y，删掉会导致 sys 库直接不可用。

2. 8.0 的 GRANT 不再顺便建用户。5.7 里 GRANT ... TO 'x'@'%' 会自动创建账号，8.0 必须先 CREATE USER，否则报 ERROR 1410。从旧项目搬过来的授权脚本常在这里断。

3. 权限表在 8.0 换成了 InnoDB。5.7 是 MyISAM，多用户授权中途失败会留下半截数据；8.0 有事务，要么全成要么全回滚。这也是为什么「直接 UPDATE mysql.user」在 8.0 更容易出问题——缓存不会自动刷新。

2.2 复制表：主从的位点存在哪

主从断开后，SHOW REPLICA STATUS 能看到位点，但这些位点同时会落进 mysql 库的几张表——它们是监控采集和崩溃恢复的依据：

表存什么
slave_master_info连源库的信息：主机、端口、复制账号、读到哪个 binlog 位置
slave_relay_log_infoSQL 线程回放到哪：relay log 文件名与位置
slave_worker_info并行复制时每个 worker 各自的位置
gtid_executed本实例已执行过的 GTID 集合
replication_asynchronous_connection_failover8.0.23+ 的源列表，配合自动故障转移
 
sql-- 主从延迟、断在哪，先看这个
SHOW REPLICA STATUS\G

-- 只有用表存位点时才有的内容（8.0 默认就是表）
SELECT * FROM mysql.slave_master_info\G

-- GTID 模式下比对差集：源库有、从库没有的事务
SELECT gtid_subtract(
  (SELECT @@global.gtid_executed), '源库的 gtid_executed');
表名没跟着术语改，别被搜索结果绕晕

MySQL 8.0.26 起，命令和系统变量里的 master / slave 改成了 source / replica：CHANGE REPLICATION SOURCE TO、SHOW REPLICA STATUS、SOURCE_HOST。但 mysql 库里这几张表的表名仍然是 slave_master_info、slave_relay_log_info、slave_worker_info，官方 8.4 文档也还是这么写。照着「新名词」去 SELECT * FROM mysql.replica_master_info 会直接报表不存在。

另外，8.0.23 起 master_info_repository 已弃用，位点只能存表（之前可以选 FILE，写成 master.info 文本）。所以老教程里「删掉 master.info 重启」的做法在 8.0 不再适用。

2.3 统计信息与优化器表：执行计划为什么这么选

这四张表决定优化器怎么估行数、怎么算成本。执行计划突然变差，很多时候是这里的统计过期了：

表作用怎么动它
innodb_table_stats表的行数、聚簇索引页数等持久化统计ANALYZE TABLE 会重写这里
innodb_index_stats每个索引的选择性、页数同上
server_cost通用操作的成本常量，如 row_evaluate_costUPDATE 后 FLUSH OPTIMIZER_COSTS
engine_cost特定存储引擎的成本，如一次页读取同上
 
sql-- 统计信息是什么时候采的、采了多少行
SELECT table_name, n_rows, clustered_index_size, last_update
FROM mysql.innodb_table_stats
WHERE database_name = 'itcast';

-- 觉得统计不准就重采（InnoDB 会更新上面两张表）
ANALYZE TABLE itcast.emp;

-- 改完成本常量必须刷，否则当前会话仍用旧值
FLUSH OPTIMIZER_COSTS;
为什么改了统计表没反应

统计信息被缓存在内存里。ANALYZE TABLE 会同时刷新缓存，但如果你是手工 UPDATE mysql.innodb_table_stats，必须再 FLUSH TABLE 表名 才会重新加载。改成本表同理，靠 FLUSH OPTIMIZER_COSTS。

2.4 日志、帮助、时区：三个不常碰但会咬人的

表说明
general_log / slow_log日志写表时的落点（CSV 引擎）。可以直接 SELECT、TRUNCATE，也可以当成普通表查
help_topic 等 4 张HELP 'SELECT' 命令的数据来源。8.0.16 起升级会自动补，更早版本要跑 mysql_upgrade
time_zone 等 5 张时区定义。默认是空的，需要手工导入
时区表是空的，所以 CONVERT_TZ 返回 NULL

新装的 MySQL 里，time_zone 系列 5 张表一行数据都没有。表现是：

SELECT CONVERT_TZ('2026-11-25 10:00:00', 'UTC', 'Asia/Shanghai');
-- 返回 NULL，不报错，最难查

-- 用偏移量则不受影响，因为不需要查表
SELECT CONVERT_TZ('2026-11-25 10:00:00', '+00:00', '+08:00');

补数据（Linux）：mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -uroot -p mysql。Windows 没有 zoneinfo 目录，需要从带时区数据的实例导出后导入。

3. information_schema：元数据的唯一入口

它不存数据，是数据字典的一扇窗。8.0 之后这扇窗几乎是必需的——因为数据字典表本身不让你读。

日常用的表就那么几张，而且基本都能对应回一条 SHOW 命令：

表查什么等价命令
SCHEMATA有哪些库、默认字符集SHOW DATABASES
TABLES表名、引擎、行数估算、大小、注释SHOW TABLES
COLUMNS字段类型、是否可空、默认值、注释SHOW COLUMNS
STATISTICS索引的列顺序、基数（CARDINALITY）SHOW INDEX
ENGINES支持哪些存储引擎、哪个是默认SHOW ENGINES
TRIGGERS / VIEWS / ROUTINES / EVENTS触发器、视图、存储过程与函数、定时事件的定义SHOW TRIGGERS 等
PARTITIONS分区表的分区边界、每个分区的行数SHOW CREATE TABLE
COLUMN_STATISTICS列直方图（8.0 新增）无
PROCESSLIST当前连接与正在执行的 SQLSHOW PROCESSLIST
 
sql-- 哪个库最大（按数据 + 索引字节数排）
SELECT table_schema,
       ROUND(SUM(data_length + index_length) / 1024 / 1024, 1) AS mb
FROM information_schema.tables
GROUP BY table_schema
ORDER BY mb DESC;

-- 找没有主键的表：主从、在线 DDL 都怕这个
SELECT t.table_schema, t.table_name
FROM information_schema.tables t
LEFT JOIN information_schema.statistics s
       ON s.table_schema = t.table_schema
      AND s.table_name   = t.table_name
      AND s.index_name   = 'PRIMARY'
WHERE t.table_schema NOT IN ('mysql', 'sys', 'information_schema', 'performance_schema')
  AND t.table_type = 'BASE TABLE'
  AND s.index_name IS NULL;
TABLE_ROWS 是估算值，还默认缓存 24 小时

看到「这张表 300 万行」先别信。InnoDB 的行数是采样估算；更麻烦的是 8.0 会缓存统计信息，information_schema_stats_expiry 默认 86400 秒，一天内都返回同一份旧值。大批量删除之后，页面上的行数可能还停在删之前。

-- 要实时值：本次会话不缓存
SET SESSION information_schema_stats_expiry = 0;
-- 或者让 InnoDB 重新采样（大表有成本）
ANALYZE TABLE itcast.emp;

真要精确行数只能 SELECT COUNT(*)。业务上做分页总数时，这一点尤其要注意。

4. performance_schema：运行时数据

前面两个库回答「结构是什么」，它回答「现在在干什么」。100 多张表，全在内存，重启 mysqld 就清零——这是它和慢日志最大的区别：慢日志能留档，它只能看当下。

sql-- 总耗时最高的 SQL（按 digest 归一化，"where id=1" 和 "where id=2" 算同一条）
SELECT digest_text,
       count_star AS exec_count,
       ROUND(sum_timer_wait / 1e12, 2) AS total_s,
       ROUND(avg_timer_wait / 1e9, 2)  AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY sum_timer_wait DESC
LIMIT 10;

-- 谁在等锁、被谁挡着（8.0 用这两张表，老的 INNODB_LOCKS 已移除）
SELECT w.requesting_thread_id AS 等待线程,
       w.blocking_thread_id   AS 阻塞线程,
       l.object_name          AS 表,
       l.lock_type, l.lock_mode
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks l
  ON l.engine_lock_id = w.blocking_engine_lock_id;
它和慢日志不是一回事

慢日志要有 long_query_time 阈值、写文件、能留档；performance_schema 是全量采样 + 聚合，不设阈值，但重启即失。查「历史某天为什么慢」要靠慢日志，查「现在谁在拖」用这里。

5. sys：把上面两张表翻成人话

sys 库里除了 sys_config 一张真表，其余 100 多个对象全是视图，数据来自 performance_schema 和 information_schema。它最大的价值是把皮秒、把 event_name 换成毫秒和中文语义。

sql-- 谁在跑：比 SHOW PROCESSLIST 多出耗时、扫描行数
SELECT thd_id, conn_id, user, db, command, time, state, LEFT(sql_text, 60) AS sql_text
FROM sys.session
WHERE command <> 'Sleep'
ORDER BY time DESC;

-- 全表扫描最多的 SQL：加索引的第一手线索
SELECT query, exec_count, no_index_used_count, rows_examined_avg
FROM sys.statements_with_full_table_scans
ORDER BY no_index_used_count DESC
LIMIT 10;

-- 建了却没人用的索引：清理候选
SELECT * FROM sys.schema_unused_indexes;

6. 查什么去哪：一张决策表

你想知道去哪查别去哪
某个账号有什么权限SHOW GRANTS FOR 'u'@'h'别手工拼 mysql.user + db + tables_priv，会漏
库/表/索引的结构information_schemamysql.tables（3554 拒绝）
表现在多大、多少行information_schema.tables（估）或 COUNT(*)（准）别信缓存的行数
现在谁在跑、谁在等锁sys.session / sys.innodb_lock_waitsSHOW PROCESSLIST 看不到锁等待关系
哪条 SQL 最耗时间sys.statement_analysis慢日志（只覆盖超阈值的）
执行计划为什么选错索引mysql.innodb_table_stats + EXPLAIN猜
主从断在哪SHOW REPLICA STATUSmysql.slave_master_info（要自己解读）
这一节真正要带走的三句

1. 只有 mysql 需要备份，另外三个是重建出来的——所以「备份整个实例」和「备份业务库」差的不只是数据量。
2. 8.0 的 mysql 库有 37 张看得见的表，元数据本体是隐藏的，必须经 information_schema 看。
3. 查现状用 performance_schema / sys，查结构用 information_schema，查账号用 mysql。

自测三问先自己答一遍，再点开对答案

Q1为什么直接 SELECT * FROM mysql.tables 会报 ERROR 3554，而 SHOW TABLES FROM mysql 里也看不到它？

这是 8.0 的数据字典隐藏表。数据字典被搬进 InnoDB 内部表后，只允许通过 information_schema 和 SHOW 访问，直查会被拦住（3554 就是这个含义）。要查表信息，走 information_schema.TABLES。

Q2想知道一张 InnoDB 表到底有多少行，查 information_schema.TABLES.TABLE_ROWS 靠谱吗？

不靠谱。这个值是采样估算，InnoDB 不会为它去数全表；而且结果会被 information_schema_stats_expiry 缓存（默认 86400 秒），可能一天都不变。要精确就 SELECT COUNT(*)，或先把该变量设为 0 再查。

Q3线上卡住了，想确认「谁在等谁的锁」，该查哪里？

查 performance_schema.data_locks 与 data_lock_waits——8.0 起它们取代了 5.7 的 INFORMATION_SCHEMA.INNODB_LOCKS / INNODB_LOCK_WAITS。懒得拼表就直接看视图 sys.innodb_lock_waits。

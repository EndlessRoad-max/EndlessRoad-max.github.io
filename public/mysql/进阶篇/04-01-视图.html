4.1视图

视图不存结果，只存一句 SELECT。这一页回答四件事：它存在哪、怎么写、什么情况下能改、为什么要有。最后一节是我自己的理解——照着它去想，比背语法有用；里面有两处我原来的说法不准，已经改过来。

进阶篇 · 4.1 更新：2026-11-28 环境：MySQL 8.0

一屏速记合上笔记，这 5 条要能自己说出来

  1. 视图 = 一条起了名字的 SELECT。定义进数据字典，数据一条都不存；每次查视图，那句 SQL 都真跑一遍——所以视图不提速，MySQL 也没有物化视图。
  2. 定义在哪看：information_schema.VIEWS（VIEW_DEFINITION / CHECK_OPTION / IS_UPDATABLE / DEFINER）或 SHOW CREATE VIEW。8.0 没有 .frm 文件了。
  3. 能不能改数据，看行是否一一对应：出现聚合/窗口函数、DISTINCT、GROUP BY、HAVING、UNION 就不能 UPDATE / DELETE。查 IS_UPDATABLE 最快。
  4. WITH CHECK OPTION 管的是「改完这行还看不看得见」，默认 CASCADED，越界报 1369。它和「能不能改」是两道闸，别混。
  5. 视图解决的是权限边界和重复查询的固化：简化、安全、数据独立。它是接口，不是缓存。

1. 它到底是什么

视图（View）是一种虚拟存在的表。行和列来自定义视图时那句查询用到的表，并且是在使用时动态生成的。通俗说：视图只保存查询的 SQL 逻辑，不保存查询结果——所以「创建视图」这件事，实质就是把那条 SELECT 写对。

顺着这张图能推出三条，后面所有规则都从它们来：

  1. 查视图 = 查基表。视图不缓存结果，基表一变立刻可见；基表被锁，视图查询一起等。
  2. 改视图数据 = 改基表。UPDATE stu_v_1 SET name='x' 改的是 student 的行，不是字典里那行文字。
  3. 建 / 改 / 删视图 = 改字典。这类 DDL 不碰业务数据，但会锁元数据，业务高峰别做。

想确认自己库里有哪些视图、能不能改，直接查这张表：

SELECT TABLE_SCHEMA, TABLE_NAME, IS_UPDATABLE, CHECK_OPTION, DEFINER,
       VIEW_DEFINITION
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'itcast';

VIEW_DEFINITION 是被重写过的文本：库名会带上反引号，SELECT * 已经展开成具体列。别拿它跟源码逐字对比，看逻辑对不对就行。

information_schema 是内置的系统库（与 mysql、performance_schema、sys 并列），但它里面的「表」不存数据，是每次查询时按数据字典现算的。所以不用 USE——表名前面已经带了库名，USE 只负责给不带库名的表指认默认库；连默认库都没有（SELECT DATABASE() 返回 NULL）时，这句照样跑。
两个坑：① 查这张表要 SHOW VIEW 权限，权限不够不报错，而是行数悄悄变少；② 手滑执行过 USE information_schema; 又忘了切回来，之后查业务表全是 1146——先 SELECT DATABASE(); 看自己在哪。

视图不加速，这一点必须先钉死

它不物化、不建索引、不缓存结果。查询时那句 SELECT 照跑，改视图不改变执行计划。少数情况下 ALGORITHM=TEMPTABLE 还要先建临时表，比直接查更慢。把视图当「优化手段」是最常见的误用。

2. 四个动作

动作语句要点
建CREATE [OR REPLACE] VIEW v(列名) AS SELECT ... [WITH CHECK OPTION]列名列表可省，省了就用 SELECT 的列名。
改ALTER VIEW v AS SELECT ... / CREATE OR REPLACE VIEW ...视图不存在时 ALTER 报错，OR REPLACE 直接建。
查SHOW CREATE VIEW v; / SELECT * FROM v;前者看定义和算法，后者看数据。
删DROP VIEW [IF EXISTS] v1, v2;一次可以删多个；不加 IF EXISTS 时不存在就报错。
 
-- 建：id 不超过 10 的学生，只取两列
CREATE OR REPLACE VIEW stu_v_1 AS
SELECT id, name FROM student WHERE id <= 10;

-- 查：一条看定义，一条看数据
SHOW CREATE VIEW stu_v_1;
SELECT * FROM stu_v_1;

-- 改：两种写法效果一样，差别只在视图不存在时
ALTER VIEW stu_v_1 AS SELECT id, name, no FROM student WHERE id <= 10;
CREATE OR REPLACE VIEW stu_v_1 AS SELECT id, name, no FROM student WHERE id <= 10;

-- 删：可一次删多个
DROP VIEW IF EXISTS stu_v_1;

SHOW CREATE VIEW 的输出里有两处别跳过：

  • ALGORITHM=MERGE：默认值。MERGE 把定义合并进外层查询（能改）；TEMPTABLE 先落临时表（一定不能改）。
  • DEFINER=`root`@`%` + SQL SECURITY DEFINER：查视图时用定义者的权限，不是你的。这是「用视图做权限」能成立的原因，也是定义者被删后视图直接报 1449 / 1356 的原因。

列名重复会报 1060 Duplicate column name；视图名和表名共用一个命名空间，同库重名报 1050 Table already exists。这两条在多表联查建视图时最容易撞上——用 AS 给同名列起别名。

3. 什么情况下能改

总闸只有一句：视图里的行，和基表里的行，必须一一对应。一行视图如果是由多行基表算出来的、或者根本找不到对应的基表行，就没法把改动写回去。

视图里出现为什么不能改
聚合函数 / 窗口函数（SUM() MIN() MAX() COUNT()、ROW_NUMBER() 等）一行视图是多行基表算出来的，反向拆不回去。
DISTINCT去重之后，不知道要改哪一行。
GROUP BY同上，行已经变成组。
HAVING条件架在分组结果上，没有对应的行。
UNION / UNION ALL一行可能来自任意一个分支。

上表是课程列的 5 条。8.0 官方文档还多几条，遇到了别以为是 bug：

  • SELECT 列表里有子查询；WHERE 里的子查询引用了 FROM 中的表。
  • 只引用常量（没有基表可写）。
  • ALGORITHM=TEMPTABLE。
  • 同一基表列被引用多次（只挡 INSERT，不挡 UPDATE / DELETE）。

不想背，直接问服务器：

SELECT TABLE_NAME, IS_UPDATABLE
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'itcast';

IS_UPDATABLE=NO 时，UPDATE / DELETE 直接报 1288 The target table ... is not updatable。YES 也只代表语法上可改，改出来是不是你要的，还得自己看数据。

3.1 多表视图的规矩

「多表视图一律不能增删改」这句是错的。至少 UPDATE 可以。三条语句规矩不同：

语句多表（内连接）视图条件
UPDATE可以SET 里只能出现同一张基表的列；改别的表那一半直接拒绝。
DELETE不行join 视图不允许 DELETE，报 Can not delete from join view。
INSERT基本不行只有单表视图才可插入；join 视图要插，必须所有分支都可合并、且只插一张表。

能用 UPDATE 的前提是视图走 MERGE：内连接（不是外连接、不是 UNION）、没有上面那五种东西。外连接视图一律只读。

就算 UPDATE 成功，也别拿多表视图当更新入口

一个学生选了三门课，三表联查的视图里他就是三行。你 UPDATE ... WHERE student_no='20190101' 会同时改三行——改的是同一张基表的同一行，改三次。逻辑上没错，但「一行视图 = 一行基表」的直觉在这里不成立，写业务代码时特别容易算错行数。

4. WITH CHECK OPTION

它解决一个很具体的问题：视图本身是个筛子，往里插一条筛不中的行，插入会成功，但插完就看不见。数据进了基表，视图里查不到——这类「黑洞数据」最难排查。加上检查选项，就是让服务器在写入时把这行拦住。

下面用同一张表把两种结局跑一遍（假设 student 其余列可空或有默认值，否则插入会先撞 1364，那是另一回事）：

-- 看不见 id > 10 的行
CREATE VIEW stu_v_1 AS SELECT id, name FROM student WHERE id <= 10;
INSERT INTO stu_v_1(id, name) VALUES (11, 'Tom');   -- 成功
SELECT * FROM stu_v_1;                              -- 查不到 11，但基表里有

-- 加上检查选项
CREATE OR REPLACE VIEW stu_v_1 AS
SELECT id, name FROM student WHERE id <= 10
WITH CHECK OPTION;

INSERT INTO stu_v_1(id, name) VALUES (11, 'Tom');   -- ERROR 1369
UPDATE stu_v_1 SET id = 11 WHERE id = 10;           -- 同样 1369：改完就看不见了

检查范围有三个取值，差别只在「视图套视图」时才显现：

写法检查谁
不写自己的 WHERE 不检查；但如果下层视图写了检查选项，下层的照样检查。
WITH LOCAL CHECK OPTION自己的 WHERE + 下层写了检查选项的那些视图的 WHERE。
WITH CASCADED CHECK OPTION（默认）自己的 WHERE + 一路往下所有视图的 WHERE，不管下层写没写。
 
CREATE TABLE t1 (a INT);
CREATE VIEW v1 AS SELECT * FROM t1 WHERE a < 2;                 -- 没写检查选项
CREATE VIEW v2 AS SELECT * FROM v1 WHERE a > 0 WITH LOCAL CHECK OPTION;
CREATE VIEW v3 AS SELECT * FROM v1 WHERE a > 0 WITH CASCADED CHECK OPTION;

INSERT INTO v2 VALUES (5);   -- 成功：LOCAL 只管 v2 自己（5>0），v1 没写检查就不管
INSERT INTO v3 VALUES (5);   -- ERROR 1369：CASCADED 把 v1 的 a<2 也算上

同一组视图，换成 v1 也写了 WITH CHECK OPTION 之后，LOCAL 和 CASCADED 结果就一样了——差别只在「下层没写」的时候冒出来。

DELETE 不受它约束，别把它想成万能的写保护

能通过视图删掉的行，本来就是视图里看得见的行，删完不存在「还符不符合条件」的问题。它约束的是 INSERT 和 UPDATE。
另外：WITH CHECK OPTION 不等于权限控制——它拦的是「不符合条件的数据」，不拦「不该改的人」。

5. 为什么要有视图

课程给了三个词：简单、安全、数据独立。每个词背后都对应一个具体的麻烦。

作用解决的麻烦怎么用
简单 三表联查的业务每天要写十几遍，条件还总变。 定义成视图，应用只写 SELECT * FROM v WHERE ...；口径变了改视图，不改代码。
安全 外包/运营要查用户表，但不能看到手机号、邮箱，更不能看到别人的行。 建视图只放需要的列 + WHERE 限定行，只把这一个视图的 SELECT 授给账号，基表权限一点都不给。
数据独立 表要拆、要改名、要加一列，应用里几十处 SQL 全得跟着改。 应用只认视图；底层改结构时改视图定义，应用不动。
「安全」这条要说得更准一点

课程原话是「数据库可以授权，但不能授权到特定行和特定列」。列级授权 MySQL 是支持的：GRANT SELECT(id,name) ON itcast.tb_user TO 'u'@'%'; 就能只给两列。
所以视图真正不可替代的是行级范围（WHERE 挑行，GRANT 做不到）和把多表逻辑收成一个名字。别把「只能看几列」当成必须用视图的理由。

「数据独立」是有限的

视图在查询时才解析，不是编译期绑定。基表删了一列，视图立刻失效，报 1356 View ... references invalid table(s) or column(s)，所有依赖它的查询一起挂。
所以「独立」的准确含义是：表结构变化的影响被收敛到视图这一处，不是「表怎么变视图都不受影响」。

6. 我的理解（含两处纠正）

下面是我自己捋的那套说法。对着图 1 一条条过，比背语法记得住。标「半步对」和「要改」的地方，是我想当然了的。

  1. 「视图本质就是一句 SQL 查询」对

    再补三个附件就完整了：一个名字、一个执行身份（DEFINER）、一组可见性规则（WITH CHECK OPTION）。这三样才是视图比「把 SQL 存在记事本里」多出来的东西。
    所以创建视图时真正要写对的只有 SELECT；名字和选项是外壳。

  2. 「底层系统库里有一张表记着视图的元数据」方向对，位置要改

    5.7 是磁盘上的 .frm 文件；8.0 换成了数据字典（藏在 mysql 库里的隐藏表，直接 SELECT 会被拒）。
    对外统一从 information_schema.VIEWS 看：VIEW_DEFINITION 存那句 SELECT，CHECK_OPTION 存检查选项，IS_UPDATABLE 存能不能改，DEFINER 存执行身份。想改这些值只有一条路——ALTER VIEW，别去动字典表。

  3. 「操作视图就是操作系统库数据或它依赖的真实表」要拆成三件事

    混在一起就会得出「改视图会改字典」这种错结论：

    查（SELECT）→ 读基表；增删改（DML）→ 写基表，字典一个字节都不动；建/改/删视图（DDL）→ 只动字典，业务数据不动。
    把这三条分清楚，后面「能不能改」「为什么插入查不到」就都顺了。

  4. 「增删改的前提是视图的行和基表的行一一对应」对，这是总闸

    聚合、DISTINCT、GROUP BY、HAVING、UNION 之所以被禁，全是因为它们破坏了「一行对一行」。记住理由比记住清单管用——清单会长，理由不会。

  5. 「涉及多表的视图，增删改直接不允许」要说错一半

    UPDATE 是可以的：内连接、走 MERGE、SET 只涉及一张基表的列。DELETE 不行，INSERT 基本不行。
    但「能改」不等于「该改」：一对多联查里一行视图对应多行基表，按视图行数去更新会算错影响行数（见 §3.1）。

  6. 「WITH CHECK OPTION 校验增删改影响的行是否还能被视图包含」基本对，补两点

    第一，它检查的是写入后的行，不是写入前帮你筛掉；不通过是整条语句失败（1369），不是「跳过这一行」。
    第二，它管 INSERT 和 UPDATE，不管 DELETE。
    还有一层容易混：「能不能改」和「改完看不看得见」是两道闸，前者决定语句允不允许执行，后者决定数据落不落得进去。

  7. 「视图的优势说明了这个功能为什么被造出来」对，而且这是最该记的一层

    技术不会凭空出现。视图出现是因为三个真实痛点：重复查询没法复用（SQL 只能复制粘贴）、权限只能到表/列、到不了行、表结构一变应用全崩。
    它没解决「查询慢」——那不是它的目标，别指望。

一句话版本

视图 = 存在字典里的一句 SELECT + 一套可见性规则 + 一个执行身份；数据始终在基表，视图只决定「你看到哪些行、哪些列、能不能写回、写完还看不看得见」。

7. 两个案例

案例一：屏蔽敏感列（安全）

开发要查用户，但手机号和邮箱不能给。建一个只含基本字段的视图，只把视图的查询权限授出去：

CREATE VIEW tb_user_view AS
SELECT id, name, profession, age, gender, status, createtime
FROM tb_user;

SELECT * FROM tb_user_view;

-- 关键一步：只授视图，并确认基表没给过
GRANT SELECT ON itcast.tb_user_view TO 'reader'@'%';
SHOW GRANTS FOR 'reader'@'%';

SHOW GRANTS 里不该出现 itcast.tb_user。出现过就用 REVOKE ... ON itcast.tb_user 撤掉（没授过就撤会报 1141）。只建视图不收回基表权限，等于白做——账号照样能 SELECT phone, email FROM tb_user。视图能当权限边界，前提是基表权限本来就没给。

案例二：固化三表联查（简化）

CREATE VIEW tb_stu_course_view AS
SELECT s.name AS student_name,
       s.no   AS student_no,
       c.name AS course_name
FROM student s, student_course sc, course c
WHERE s.id = sc.studentid
  AND sc.courseid = c.id;

SELECT * FROM tb_stu_course_view WHERE student_no = '20190101';

三个表连起来、列名还重了（student.name 与 course.name），所以必须起别名，否则 1060。这类视图只当查询入口：一个学生多门课，行不一一对应，别拿它做更新。

案例二还有个隐性代价

视图把「口径」藏起来了。哪天有人改了视图定义，所有依赖它的业务一起变，而代码里看不出来。所以：视图定义要进版本管理，改之前先 SHOW CREATE VIEW 存一份。视图降低重复，也隐藏了变化。

自测三问先自己答，再展开对照

Q1视图里的数据存在哪？为什么基表一改，视图里立刻就变了？

一条都不存。字典里只有那句 SELECT 的文本、检查选项和执行身份。
查视图时服务器把定义展开成对基表的查询，所以读到的永远是基表当下的数据——没有缓存，也就没有「刷新视图」这回事。

Q2SELECT dept, COUNT(*) FROM emp GROUP BY dept 做成视图，能 UPDATE 吗？

不能。GROUP BY 加聚合函数，一行视图是多行基表算出来的，IS_UPDATABLE 是 NO，UPDATE 直接报 1288 The target table ... is not updatable。
想看这类统计只能查，要改就回基表改。

Q3视图条件是 id <= 10 但没写 WITH CHECK OPTION，INSERT ... (11,'Tom') 会怎样？

插入成功，但视图里查不到这行。数据在基表里，等于给自己埋了个「黑洞」。
加上 WITH CHECK OPTION 后同样的语句报 1369 CHECK OPTION failed，整条失败、一行不写。线上建视图，除非你很确定不需要，否则都加上。

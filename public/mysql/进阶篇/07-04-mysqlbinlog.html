7.2.3mysqlbinlog

截图第一句说得很准：binlog 是二进制格式保存的，想看成文本就要用它。但它和前面三个工具不是一类东西——mysql、mysqladmin 是「连上服务器干活」，mysqlbinlog 默认是「读本地的一堆字节」，连密码都不用给。理解这一点，后面那些奇怪现象（默认输出一堆 base64、-v 不加就看不见 SQL、输出不能直接回放）才串得起来。

进阶篇 · 7.2.3 更新：2026-11-25 环境：MySQL 8.0（默认 binlog_format=ROW）

一屏速记合上笔记，这 5 条要能自己说出来

  1. 它读的是磁盘上的 binlog 文件，默认不连数据库；要远程拉才加 -R --read-from-remote-server。
  2. 8.0 默认 binlog_format=ROW，行变更被记成二进制镜像，所以默认输出一堆 base64；要可读就加 -v --base64-output=DECODE-ROWS。
  3. 回放前确认 binlog_row_image=FULL：设成 MINIMAL 就只记被改的列，回放出来的行不完整。
  4. --start-datetime / --stop-datetime 用的是运行 mysqlbinlog 这台机器的本地时区，不是数据库服务器的时区。
  5. 时间点恢复的公式：最近一次全备 + 从备份点回放到误操作前一秒的 binlog；回放需要 BINLOG_ADMIN 权限。

1. 它读文件，不连数据库

binlog 文件本身是自描述的：文件头有 magic number，每个事件前有 19 字节的公共头（时间戳、类型、server_id、长度、下一个事件的位置）。所以 mysqlbinlog 完全可以离线解析，不需要 mysqld 在跑，也不需要账号密码——只需要对这个文件有读权限。

只有两种情况下它才需要连服务器：加了 --read-from-remote-server（-R），或者文件被加密了（本地解不开，只能让服务器解密后传过来）。

sql-- 先搞清楚去哪找文件、有哪些文件
SHOW VARIABLES LIKE 'log_bin%';      -- log_bin_basename 就是路径前缀
SHOW BINARY LOGS;                    -- 当前还有哪些 binlog，多大，是否加密
SHOW MASTER STATUS;                   -- 现在写到哪个文件、哪个位点（8.4 改用 SHOW BINARY LOG STATUS）

2. 语法：位置参数是文件

截图给的语法是 mysqlbinlog [options] log-files1 log-files2 ...。和前面几个工具比，最大的结构差异在这里：位置参数是文件，而且可以有多个，按给定顺序依次读，效果等于把它们首尾拼成一条时间线。

3. 截图六个选项逐个校正

截图那六行里有三行写得不够准，照抄会在关键时候卡住。逐条对一遍：

选项截图说法实际行为
-d / --database=name 指定数据库名称，只列出指定的数据库相关操作 要看格式。STATEMENT 格式下按「当前默认库」判断，USE 过才算；ROW 格式下按「改的是哪个库的表」判断，与 USE 无关。另外它过滤不掉 Rows_query 事件——开了 binlog_rows_query_log_events 时，别的库的原始 SQL 还会漏出来
-o / --offset=# 忽略日志中的前 n 行命令 跳过的前 N 个事件（event）。不是 N 行文本，也不是字节偏移。想看「从某处开始」应该用 --start-position，-o 基本只用于调试
-r / --result-file=name 把文本格式日志输出到指定文件 对。补充一点：Windows 上应该用它而不是 > 重定向——重定向会把 \n 转成 \r\n，回放时报语法错
-s / --short-form 显示简单格式，省略一些信息 它省略的不只是「一些信息」，而是所有行事件。ROW 格式下加 -s，输出几乎是空的。官方标注「仅供测试，不要用于生产」，且已弃用
--start-datetime / --stop-datetime 指定日期时间内的所有日志 对，但取的是运行 mysqlbinlog 那台机器的本地时区。在 UTC 的跳板机上按北京时间写参数，会整整错 8 小时
--start-position / --stop-position 指定位置间隔内的所有日志 对。位置是文件内的字节偏移，不是事件序号；而且 --stop-position 不包含从该位置开始的事件

截图之外，真正每天会用到的是下面这几个：

选项作用
-v / --verbose把行事件重建成带注释的伪 SQL。给两次（-vv）额外输出列类型和元数据注释
--base64-output=DECODE-ROWS配合 -v，把 BINLOG '...' 那坨 base64 换成伪 SQL。只适合看，不能回放
--skip-gtids输出里去掉 GTID 赋值。回放到已有 GTID 的实例时几乎是必加项
-R / --read-from-remote-server不读本地文件，从服务器拉
--raw配合 -R，把远端 binlog 原样落成本地文件（做 binlog 备份用）
--stop-never配合 -R，连上不退出，像从库一样持续追
--verify-binlog-checksum校验文件完整性，坏了会报错。恢复前先跑一遍
--include-gtids / --exclude-gtids按 GTID 集合筛选，比按位置精确
-D / --disable-log-bin输出里加上 SET sql_log_bin=0，防止回放时又写进本机 binlog，造成循环

4. 为什么默认是一堆 base64

这是新手最容易以为「工具坏了」的地方。MySQL 8.0 的 binlog_format 默认是 ROW：binlog 里存的不是 SQL 语句，而是「哪张表的哪一行，从什么值变成什么值」。这种数据用二进制编码，直接打印出来就是一段 base64。

所以不加参数直接跑，看到的是 BINLOG 'FyY2Zg8B...' 这样的块。它不是乱码，是完整的行变更数据，只是给程序看的。要变成人眼能读的伪 SQL，加 -v：

读输出时会遇到几种固定事件，认清它们能省很多猜测：

输出里看到含义
Format_desc每个 binlog 文件的第一个事件，记录服务器版本和 binlog 版本（目前是 4）
Previous_gtids / Anonymous_GtidGTID 相关。Anonymous_Gtid 说明这条事务没分配 GTID
Query（BEGIN / COMMIT / DDL）DDL 和事务边界一定以 Query 事件出现，DDL 在 ROW 格式下也是明文 SQL
Table_map把 table_id 映射到「库.表」。行事件只带 id，不带表名
Write_rows / Update_rows / Delete_rows增、改、删。这就是被 base64 包住的那部分
Xid事务提交，对应 InnoDB 的 transaction id
找误操作时有个现成技巧

DDL 是明文，所以 DROP TABLE、TRUNCATE、ALTER 这类操作不用加 -v 也能 grep 到。真正需要解码的是 DML（误 UPDATE / 误 DELETE），那种才要 -v --base64-output=DECODE-ROWS。

5. 三种形态，只有一种能回放

这一点最容易出事。-v 生成的伪 SQL 每一行都以 ### 开头，在导入 mysql 时是注释——也就是说，把带 DECODE-ROWS 的输出管道给 mysql，行变更会静默地全部丢掉：表结构恢复了、DDL 执行了，数据却一条没回来，而且没有任何报错。

官方对此的原话是：如果打算把输出重新执行，自动显示 BINLOG 语句是唯一安全的行为。其余取值只建议用于调试和阅读。

6. 时间点恢复（PITR）

这是 mysqlbinlog 存在的根本原因：全备只能恢复到备份那一刻，备份之后、出事之前的数据只能靠 binlog 补回来。流程固定为三步——恢复全备、找到边界位置、回放区间。

完整的一次操作，按顺序敲：

shell# 0) 先确认文件没坏，再往下走
mysqlbinlog --verify-binlog-checksum /var/lib/mysql/mysql-bin.000007 > /dev/null

# 1) 找误操作的边界：DDL 是明文，不用加 -v 也能 grep 到
mysqlbinlog --no-defaults /var/lib/mysql/mysql-bin.000007 | grep -n -B4 -A2 "DROP TABLE"

# 2) 找全备记录的位点（mysqldump 的文件头里有这一行）
grep -m1 "CHANGE MASTER\|CHANGE REPLICATION SOURCE" full_20261125.sql

# 3) 恢复全备
mysql -uroot -p < full_20261125.sql

# 4) 回放：区间左端取全备位点，右端取 DROP 的 # at，跳过 GTID
mysqlbinlog --start-position=193 --stop-position=47537478 --skip-gtids \
  /var/lib/mysql/mysql-bin.000007 | mysql -uroot -p

# 5) 只是想看内容，别管道给 mysql
mysqlbinlog -v --base64-output=DECODE-ROWS /var/lib/mysql/mysql-bin.000007 > look.sql
回放前必查的三件事

1. 目标实例是不是同一个。回放要在隔离实例或已恢复的空库上做，往生产库上打一遍等于把历史重演一次。
2. GTID 会不会撞。目标实例 gtid_mode=ON 且已执行过这些事务时会报 ERROR 1837，加 --skip-gtids 让它们按匿名事务执行。
3. binlog_row_image 是不是 FULL（默认就是）。如果被改成 MINIMAL，DELETE 事件里只有主键，被删掉的整行内容根本没记录，这时候谁也恢复不出来。

7. 两个前提：版本与权限

版本不能比服务器旧。binlog 格式会随版本演进，老工具读不了新事件。三个具体的分界线：

服务端版本新特性老 mysqlbinlog 的后果
8.0.14+binlog 加密（binlog_encryption=ON）报 ERROR: Reading encrypted log files directly is not supported.，只能改用 -R 让服务器解密
8.0.20+事务压缩（binlog_transaction_compression=ON）读不出压缩载荷，表现为「新写的事务全都看不见」；需要 8.0.20 及以上的 mysqlbinlog 自动解压
8.0.26+复制术语改 SOURCE / REPLICA不影响读文件，但 SHOW MASTER STATUS 之类的命令名变了

权限只在 -R 时才需要，而且要两个：

  • REPLICATION CLIENT —— 用来 SHOW BINARY LOGS，否则连「有哪些文件」都问不出来
  • REPLICATION SLAVE —— 用来建立 dump 连接拉事件流。只给一个都会卡在中间

还有一个更隐蔽的权限：把输出管道给 mysql 回放时，执行 BINLOG '...' 语句需要 BINLOG_ADMIN（旧版是 SUPER），或者 REPLICATION_APPLIER 加上每条事件的执行权限。用普通账号回放会报权限错误，而此时数据可能已经部分导入了。

8. 报错对照

现象原因怎么办
unknown variable 'default-character-set=utf8mb4' 它只认 [client] 段里的部分选项，不是所有 mysql 客户端选项都吃 把 --no-defaults 放最前面；或把该项从 [client] 挪到 [mysql]
ERROR: Reading encrypted log files directly is not supported. binlog 开了加密，本地文件是密文 改 -R --host=… --user=… --ssl-mode=REQUIRED，让服务器解密后传
输出里只有几行 base64，看不到 SQL 8.0 默认 ROW 格式，这是正常现象 加 -v --base64-output=DECODE-ROWS（只用于看）
加了 -s 之后输出几乎空了 --short-form 会丢掉所有行事件 别用它。正式参数是 -v / -vv
ERROR 1045 Access denied（用 -R 时） 缺 REPLICATION SLAVE 或 REPLICATION CLIENT GRANT REPLICATION CLIENT, REPLICATION SLAVE ON *.* TO …
ERROR 1837 … GTID_NEXT cannot be ANONYMOUS 回放流里的 GTID 与目标实例已执行集合冲突 加 --skip-gtids；或在隔离实例上先清空 GTID 历史
ERROR 1062 Duplicate entry 起点位点比备份更早，已存在的数据被重复插入 核对全备里记录的位点，别用「差不多」的数字。不要加 --force 硬推过去
Could not find first log file name in binary log index file 指定的文件已被 purge，或 .index 与实际文件不一致 先 SHOW BINARY LOGS 看还剩哪些；已删的只能从备份里找
回放没报错，但数据没回来 输出带了 --base64-output=DECODE-ROWS，行变更全是注释 重跑，去掉这个参数
这一页要带走的三句

1. 它默认只读本地文件，不需要账号；只有 -R（或文件加密）才连服务器、才要 REPLICATION 权限。
2. 8.0 默认 ROW 格式，看到 base64 是正常的，-v --base64-output=DECODE-ROWS 是为了看，不是为了回放。
3. 回放的输出不能带 DECODE-ROWS，否则数据被注释掉、静默丢失；配合 --stop-position + --skip-gtids 才是可用的 PITR。

自测三问先自己答一遍，再点开对答案

Q18.0 上直接 mysqlbinlog binlog.000003，满屏 base64 看不懂，怎么变成人话？

默认 ROW 格式把行变更存成二进制镜像，所以先按 base64 输出。加 -v 会额外解码成 ### 注释形式，再配 --base64-output=DECODE-ROWS，就能逐行看到「改了哪张表、哪一列、旧值和新值」。

Q2在 A 机器上按 09:00~09:10 过滤，切出来的内容和预期对不上，最可能是什么原因？

--start-datetime 按执行 mysqlbinlog 那台机器的本地时区解释时间。机器时区和业务记录的时区不一致，窗口就整体偏移了；先对齐时区，或改用 --start-position 精确定位。

Q3回放时抛 ERROR 1837 ... GTID_NEXT，怎么处理？

目标实例上已经有这些 GTID，回放时撞上了。恢复场景加 --skip-gtids，让 binlog 剥掉 GTID 再执行；注意这只适合「单机把数据救回来」，搭主从时不能这么绕。

常备任务剧本

知识点回答「它是什么」，剧本回答「下一步做什么」。这一页把 07 章那批工具按任务重排成三条能照着做的流程：备份、恢复到某一秒、换机器迁移。每条都标了哪一步不能跳。

跨章汇总 · 串联 7.2 全部工具 更新：2026-11-25 环境：MySQL 8.0

一屏速记动手之前先记住这 5 条

  1. 三条剧本共用一句话：先冻结现场，再动手。任何恢复动作的第一步都不是敲命令，而是让数据别再变。
  2. 备份必须同时记下位点或 GTID，否则「全备 + binlog」没有起点，剧本 B 根本没法开始。
  3. 恢复永远先恢复到临时实例，校验通过再决定怎么回灌。直接在原库上回放，等于把事故做第二遍。
  4. 迁移先对齐版本和几个初始化参数（lower_case_table_names、字符集、时区），跨大版本走 upgrade checker，别指望降级。
  5. 三条流程的收尾都是核对数字：库数、表数、行数、账号数、routine 数。对不上就不算完成。

剧本 A　每天备份一台生产库

目标：产出一个「能用来恢复」的备份，而不是「一个文件」。判断标准只有一个——把它导进空实例，数据对得上。

  1. 确认备份账号够用

    至少要 SELECT、LOCK TABLES、SHOW VIEW、TRIGGER；要导存储过程和事件，还得有对应对象的读权限。权限不够时 mysqldump 会在中途报错退出，别只看文件有没有生成，要看退出码。

  2. 一条命令导出 
    shellmysqldump -uroot -p \
  --single-transaction --quick \
  --routines --triggers --events \
  --set-gtid-purged=OFF --default-character-set=utf8mb4 \
  --result-file=/backup/itcast_$(date +%F).sql \
  -B itcast

    --quick 边读边写，不把整张表塞进内存；--result-file 由客户端自己写文件，绕开 Windows 下 > 会写出 UTF-16 的坑。

  3. 校验文件，看三条硬指标 
    shelltail -2 dump.sql                  # 末尾应有 -- Dump completed
grep -c '^CREATE TABLE' dump.sql  # 表数量和库里一致
grep -c '^INSERT INTO'  dump.sql  # 不能是 0
  4. 同一时刻把位点一起记下来 
    shellmysql -uroot -p -e "SHOW MASTER STATUS\G" > /backup/itcast_$(date +%F).pos

    8.2 起官方文档把它改称 SHOW BINARY LOG STATUS。位点和备份文件必须存一起，分开放迟早会错配。

  5. 演练一次恢复

    把文件导进一台临时实例，核对库数、表数、行数。没演练过的备份只能算「一个文件」——真正的备份是「验证过能恢复的数据」。

这一步最容易翻车

① 漏 --routines --triggers --events：不报错，恢复完才发现业务逻辑全没了。
② 只备份不记位点：出事后只能回到备份那一刻，中间的数据全丢。
③ 备份和数据库放同一台机器：机器没了，备份跟着一起没。至少异地留一份。

剧本 B　把库恢复到某一秒

触发场景：误 DELETE、误 DROP、批量刷错数据。核心公式是最近一次全备 + 从备份位点回放到误操作前一秒的 binlog。

  1. 先停写入，冻结现场 
    sqlSET GLOBAL super_read_only = ON;   -- 8.0：连 SUPER 也一起挡住

    生产上通常是应用侧先摘流量，再执行这条兜底。这一步不做，你一边恢复、数据一边在变，切出来的边界永远不可信。

  2. 定位误操作发生在哪一刻 
    shellmysqlbinlog -v --base64-output=DECODE-ROWS \
  --start-datetime='2026-11-25 09:00:00' /var/lib/mysql/binlog.000042 \
  | grep -n -B2 -A4 'DELETE FROM `itcast`.`city`'

    -v 是把行事件解成可读注释，专门用来看。找到那条语句前面的 at NNN，它就是回放的终点。

  3. 把最近的全备恢复到临时实例（3307），不碰现网 
    shellmysql -h 127.0.0.1 -P 3307 -uroot -p < /backup/itcast_2026-11-25.sql
  4. 从备份位点回放到误操作前一秒 
    shellmysqlbinlog --start-position=1234 --stop-datetime='2026-11-25 09:19:59' \
  /var/lib/mysql/binlog.000042 \
  | mysql -h 127.0.0.1 -P 3307 -uroot -p

    回放这条命令不加 -v：要的是原始事件，不是给人看的注释。看和回放永远是两条命令。

  5. 校验，再决定怎么回灌 
    sqlSELECT COUNT(*) FROM itcast.city;   -- 与业务侧记录的总数比对

    对得上再用 INSERT ... SELECT（同实例）或导出缺失行回灌到现网；对不上就重来一遍，别急着切。

这一步最容易翻车

① 直接在原库上回放 → 等于把事故做第二遍，而且这次连备份都救不回来。
② --stop-datetime 按执行 mysqlbinlog 那台机器的本地时区解释，时区不对就切多或切少。
③ 全备和 binlog 不是同一实例、位点接不上 → 回放报错或数据错位；GTID 冲突加 --skip-gtids。

剧本 C　换机器迁移整个实例

目标：把一台机器上的库整体搬到另一台，业务只感知到一次短暂断写。

  1. 先对齐版本和三个「只能在初始化时决定」的参数

    目标机同大版本最稳；跨大版本先跑 MySQL Shell 的 upgrade checker（util.checkForServerUpgrade()），MySQL 不支持降级。
    lower_case_table_names 只能在初始化时设定——源机是 0、目标机是 1，大小写表名当场打架。

  2. 导出整实例 
    shellmysqldump -uroot -p -A --single-transaction \
  --routines --triggers --events --set-gtid-purged=OFF \
  --result-file=/backup/all_2026-11-25.sql

    -A 会连 mysql 系统库一起导，账号和授权也在里面——省事，也埋着坑（见下）。

  3. 导入 
    shellmysql -uroot -p < /backup/all_2026-11-25.sql
mysql -uroot -p -e "FLUSH PRIVILEGES;"

    导入了授权表就必须刷新一次权限缓存，否则新账号要等到下次重启才生效。

  4. 核对对象数量，逐项对数 
    sqlSELECT COUNT(*) FROM information_schema.SCHEMATA;
SELECT COUNT(*) FROM information_schema.TABLES
 WHERE TABLE_SCHEMA NOT IN ('mysql','sys','information_schema','performance_schema');
SELECT COUNT(*) FROM information_schema.ROUTINES;
SELECT COUNT(*) FROM information_schema.TRIGGERS;
  5. 追增量，然后切流量

    源库 super_read_only=ON → 导出最后一段 binlog 并在目标机回放 → 再对一次数 → 切连接串 / DNS。切换前把回滚方案写清楚：切回去要多久、怎么切。

这一步最容易翻车

① -A 带着 mysql 库，目标机已有的 root@localhost 会撞主键。只想迁业务库就用 --databases db1 db2，账号单独 CREATE USER 重建。
② 时区表 mysql.time_zone* 没导 → 所有 CONVERT_TZ() 返回 NULL。
③ 字符集 / 排序规则不一致 → 索引失效或乱码，导入前先统一到 utf8mb4。

三条通用规矩

Rule 01

先冻结，再动手

恢复的第一步永远是让数据停止变化：super_read_only、摘流量、锁表都行。现场不稳，后面每一步都白做。

Rule 02

只在副本上操作

恢复、试导入、试升级，一律先进临时实例。校验通过才碰现网——现网不是试验场，只有一次机会。

Rule 03

收尾必须对数

库数、表数、行数、账号数、routine 数，一项一项比。说不出「对得上」三个字，就不算完成。

自测三问先自己答一遍，再点开对答案

Q1线上误删了 1000 行，第一件事做什么？

冻结现场：SET GLOBAL super_read_only=ON，或应用侧先摘流量。不是先 dump，也不是先回放 binlog——数据还在变，切出来的边界就不可信，越救越乱。

Q2只有一份全量备份、没有记位点，还能恢复到误删前一秒吗？

不能。全备只到备份那一刻，要往后追必须有起始位点或 GTID。这正是剧本 A 第 4 步存在的意义：位点必须和备份同时记下来，否则备份只能回到过去，回不到「刚才」。

Q3用 -A 备份迁到新机器，导入时报账号相关错误，为什么？

-A 会把 mysql 系统库一起导出，里面有源机的账号和授权；目标机已有的 root@localhost 等记录会撞主键。只迁业务库改用 --databases db1 db2，账号用 CREATE USER 重建更干净。

为什么按任务组织，而不是按工具

按工具排，你会知道「mysqldump 有哪些参数」；按任务排，你才知道「库删了现在该敲哪一条」。前一种是考试时的记忆，后一种是出事时的动作——两套都要有，但真正救命的是后者。

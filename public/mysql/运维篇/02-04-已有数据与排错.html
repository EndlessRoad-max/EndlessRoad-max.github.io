02-04已有数据与排错

课程从空库开始搭，真实环境里主库早就有数据了。这一页补两件事：怎么把历史数据接上，以及没同步时按链路往下查而不靠猜。

环境：MySQL 8.0.32 起前置：02 的四步已做完、复制尚未启动整理：2026-11-26

一屏速记合上笔记，这 4 条要能自己说出来

  1. 历史数据不会自己流过来。从当前位置启动，只接得上之后的新变更，而且不报错。
  2. 顺序固定：带坐标的快照 → 导入从库 → 用这份快照的坐标启动。坐标与快照必须同源。
  3. 排错按链路走：连上了吗 → 收到了吗 → 应用了吗 → 查的是不是那台库。
  4. 延迟不能只看一个数。Seconds_Behind_Source 的 0 和 NULL 都不代表追平，要看收发两条坐标。

1. 三条路，先选一条

把主库现有数据搬成从库的起点，只有三种做法。本页把第一种写全，另两种只给适用场景——细节各自不同，别混着抄命令。

做法适合代价与限制
mysqldump
逻辑备份		几十 GB 以内、要跨小版本、只想搬部分库或部分表。导出要读全表，导入是重新执行 SQL，慢；大表导入期间从库基本不可用。
Clone Plugin
8.0.17 起内置		整实例、同版本、几百 GB 的大库。物理页拷贝，比逻辑导入快一个量级。要求源端可连、两端插件可用、磁盘够；只搬整实例，不能挑库。
物理备份
xtrabackup 等		已有备份体系，想直接用备份做基线。工具与版本要匹配；备份必须带 binlog 坐标，否则还得另找起点。
不选也行，但别选错

「先启动复制，再手工补历史数据」不是第三条路——两边的写入顺序会错，重复键和缺行会一起出现。要么快照打底，要么整库重建。

2. 带坐标的快照

前提：主库配置、复制账号、从库配置已完成（02 主库四步 / 从库五步的前两步），复制尚未启动；GTID 为 OFF；要复制的库是 db01，表都是 InnoDB；从库没有要保留的同名数据。

  1. 导出快照，让工具把坐标写进文件主库 · Linux 终端 
    mysqldump -u root -p \
  --single-transaction --source-data=2 \
  --set-gtid-purged=OFF \
  --routines --events --triggers \
  --databases db01 \
  --result-file=/tmp/db01-seed.sql

grep -m 1 -E '^-- CHANGE (REPLICATION SOURCE|MASTER)' /tmp/db01-seed.sql

    --single-transaction 给 InnoDB 拿一致快照；--source-data=2 把坐标写成注释（=1 会写成可执行语句，导入时会改掉从库的复制配置）；本页不开 GTID，所以 --set-gtid-purged=OFF。

    命令正常结束、文件非空、能 grep 到含文件名和位置的注释。把这行抄下来——后面不要再用新的 SHOW MASTER STATUS 覆盖它。

    导出开始时会短暂取全局读锁，长事务会让它等；导出期间不要做 DDL。非 InnoDB 表不受这个快照保护，会被单独加锁读。

  2. 传到从库并导入主库 · Linux 终端 
    # replica_os_user 换成从库的系统账号
scp /tmp/db01-seed.sql replica_os_user@192.168.200.201:/tmp/db01-seed.sql
    从库 · mysql 客户端（管理员） 
    -- 此刻没有业务连接、没有在跑的复制通道
SET GLOBAL super_read_only = OFF;
SET GLOBAL read_only = OFF;
SET SESSION sql_log_bin = 0;
SOURCE /tmp/db01-seed.sql;
SET SESSION sql_log_bin = 1;
SET GLOBAL super_read_only = ON;

    sql_log_bin = 0 让这段导入不写进从库自己的 binlog——否则将来这台从库被提升为主库，会把这些行再发一遍。

    最后一条会同时打开 read_only。导入没报错再抽查 db01 的表和数据量；失败就先恢复只读、修好再继续，别带病启动复制。

    从库若开了事件调度器，保持 event_scheduler=OFF，别让导进来的定时任务自己跑。

  3. 用快照的坐标启动从库 · mysql 客户端 
    CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '192.168.200.200',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'itcast',
  SOURCE_PASSWORD = 'Root@123456',
  SOURCE_LOG_FILE = 'binlog.000010',   -- 抄备份注释里的值
  SOURCE_LOG_POS  = 984,               -- 同上
  SOURCE_SSL = 1;

START REPLICA;
SHOW REPLICA STATUS\G

    已有的库和表不要重建，从库现在就是这个状态，接着往后应用即可。

3. 没同步，按链路查

在从库执行 SHOW REPLICA STATUS\G，顺着链路走一遍：连上了吗 → 收到了吗 → 应用了吗 → 查的是不是该看的数据。

现象第一步
Empty set确认连的是从库（@@hostname、@@port），并确认 CHANGE REPLICATION SOURCE 真的执行成功了。
Replica_IO_Running 为 No 或 Connecting先读 Last_IO_Error。超时/拒绝：地址、监听、端口、防火墙；1045：账号来源或密码；SSL 类报错：TLS 配置。最快的办法是把主库那段手工连接重跑一次。
Replica_SQL_Running: No读 Last_SQL_Error。1062 多为重复键，1032 多为找不到行——先查从库是否被误写、初始数据是否缺失，不要直接跳过事务。
报日志不存在 / 已清理核对完整报错、源地址、文件名与位置。需要的 binlog 已被清理，只能从备份重新初始化；1236 不是单一原因，别看到它就照同一个方案改。
报主从 UUID 相同通常是直接拷了数据目录。可重建的从库优先重新初始化，别在运行中手改 auto.cnf。
两个 Yes，但查不到新数据确认主库事务已提交、连的地址对、在新事务里重查；再查复制过滤、延迟、以及初始数据缺口（本页第 1 节的坑）。
从库能写进数据只读没生效。检查 read_only / super_read_only；已经写进去的脏数据要先评估，别直接让它复制回主库。

4. 延迟怎么判

Seconds_Behind_Source 只能当参考：0 不代表追平（接收早断了，或者本地刚好应用完），NULL 也不代表零延迟。

SHOW REPLICA STATUS\G
-- 收到哪了：Source_Log_File + Read_Source_Log_Pos
-- 应用到哪：Relay_Source_Log_File + Exec_Source_Log_Pos

两对数都带文件名，不能只把两个数字相减：跨文件时数字会回退。

表现常见原因
收得快、用得慢大事务（几万行一个事务）、DDL、从库上还有查询在抢资源、单线程应用追不上主库并发。
收得慢网络带宽或延迟、主库 Dump 线程被大事务阻塞、binlog 太大。
应用卡住不动锁等待、唯一键冲突、表上没有可用索引导致逐行回表扫。

确认是「收得快、用得慢」之后，再去看大事务、锁等待、表上有没有可用索引、CPU 和磁盘 I/O。先找瓶颈，再谈并行参数：8.0.27 起 replica_parallel_workers 默认 4，但把线程数调大不会让一条大事务变快。

5. worker 报错，怎么看到具体原因

并行应用时，Last_SQL_Error 可能只说某个 worker 失败，细节在这里：

SELECT CHANNEL_NAME, WORKER_ID, SERVICE_STATE,
       LAST_ERROR_NUMBER, LAST_ERROR_MESSAGE
FROM performance_schema.replication_applier_status_by_worker
WHERE LAST_ERROR_NUMBER <> 0;

在从库查。改连接参数前先 STOP REPLICA;，改完再 START REPLICA;——不要把旧坐标重新抄一遍，那会让它从旧位置重放。

自测三问先自己答，再展开对照

Q1为什么必须用「快照里的坐标」，而不是启动前再查一次 SHOW MASTER STATUS？

快照是某一刻的一致视图，坐标必须和它对齐。启动前再查一次，两者之间发生的变更既不在快照里、也不会被重放——那段数据就永久缺失。
导出完成后坐标就固定了，中间有新写入不影响，重放会补上。

Q2导入从库时为什么要 SET SESSION sql_log_bin = 0？

防止这段导入写进从库自己的 binlog。否则将来这台从库被提升为主库、或挂了下级从库，这些行会被再发一遍，造成重复。
注意它是 session 级，只影响当前连接；导入完记得开回来。

Q3Seconds_Behind_Source 显示 0，能说明从库追平了吗？

不能。它算的是「应用时间」与「主库当前时间」的差，接收已经断掉、或本地刚好应用完时，都可能显示 0；8.0 里还可能是 NULL。
判断进度只能看收发两条坐标，并确认 Replica_IO_Running 是 Yes。

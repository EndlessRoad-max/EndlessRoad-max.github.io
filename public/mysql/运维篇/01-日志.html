01日志

MySQL 有四种常用日志，各自回答不同的问题：为什么起不来（错误日志）、数据是怎么变成现在这样的（二进制日志）、客户端到底发了什么（查询日志）、哪条 SQL 慢（慢查询日志）。搞不清谁记什么，排障时就会在错的账本里翻半天。

运维篇 · 01 日志 更新：2026-11-25 环境：MySQL 8.0

一屏速记合上笔记，这 5 条要能自己说出来

  1. 四个日志的默认开关不一样：错误日志、二进制日志默认开；查询日志、慢查询日志默认关。排障第一步不是查，而是先确认这个日志到底有没有在记。
  2. 二进制日志只记会改数据的语句（DDL + DML），不记 SELECT。所以它不能当审计日志用——查不到谁读了什么。
  3. binlog 的文件名 = log_bin_basename + 6 位编号（从 000001 起），log_bin_index 是这些文件的清单。编号只增不减，PURGE 之后也不回退。
  4. 清理三种方式：PURGE BINARY LOGS TO/BEFORE、RESET MASTER（8.0.34 起弃用）、按 binlog_expire_logs_seconds 自动过期（默认 30 天）。PURGE 前必须确认从库已经读完，否则从库直接断。
  5. 慢查询日志的判定是两道条件同时满足：耗时 ≥ long_query_time（默认 10 秒）且扫描行数 ≥ min_examined_row_limit（默认 0）。只调阈值不看扫描行数，会漏掉真正该优化的 SQL。

1. 四本账的分工

先建立一张全局图。四种日志写的是同一个实例的不同侧面，互相不能替代：

日志系统变量开关默认默认落点能否动态开启
错误日志log_error开（无法关闭）Linux 包：/var/log/mysqld.log否，静态参数
二进制日志log_bin开数据目录 binlog.000001否，要重启
查询日志general_log关host_name.log（数据目录）能，SET GLOBAL
慢查询日志slow_query_log关host_name-slow.log（数据目录）能，SET GLOBAL
两个「关着」的日志，是新手最容易白查的原因

业务说「这条 SQL 慢得要死」，你打开慢查询日志发现是空的——不是没慢 SQL，是日志根本没开。同理，怀疑 ORM 拼错了语句去翻查询日志，发现文件不存在。
所以任何一次排障，第一步都是同一句话：SHOW VARIABLES LIKE '%log%'; 先确认账本存在，再谈内容。

2. 错误日志：唯一记「服务器自己」的账

错误日志是四种里最特殊的一个：它不记 SQL，记的是 mysqld 这个进程的状态——启动参数解析、InnoDB 崩溃恢复、端口占用、磁盘写满、表损坏、连接被拒。它默认开启，而且没有关闭开关，只能改路径或重定向。

sql-- 路径、级别、组件链，三个一起看
SHOW VARIABLES LIKE '%log_error%';
-- +------------------------------+---------------------------------+
-- | log_error                   | /var/log/mysqld.log            |
-- | log_error_services          | log_filter_internal;log_si…    |
-- | log_error_suppression_list  |                                |
-- | log_error_verbosity         | 2                              |
-- +------------------------------+---------------------------------+

-- 日志里的时间对不上系统时间？查这个
SELECT @@log_timestamps;   -- 默认 UTC，写进文件的时间比北京时间早 8 小时
SET PERSIST log_timestamps = 'SYSTEM';
shell# 路径不是固定的：先问服务器，别猜
mysql -uroot -p -N -B -e "SELECT @@log_error"

# 起不来的时候，只看最后 200 行，够定位 95% 的启动失败
tail -n 200 /var/log/mysqld.log
grep -i "error" /var/log/mysqld.log | tail -n 50

# 轮转：先改名再 flush，否则新日志接着往同名文件里写
mv /var/log/mysqld.log /var/log/mysqld.log.20261125
mysqladmin -uroot -p flush-logs
默认路径随安装方式变，不要背死

官方 RPM / YUM：/var/log/mysqld.log；Debian / Ubuntu：/var/log/mysql/error.log；源码编译或自定义：数据目录下的 host_name.err。
课程里写的「默认 /var/log/、文件名 mysqld.log」是按 RPM 包讲的，换个装法就不成立。永远以 SELECT @@log_error 为准。

错误日志里常看到的几行，认得出来能省很多时间

[ERROR] [MY-010119] Aborting + 上面几行 InnoDB 报错 → 崩溃恢复失败，看它前面那条真正的错。
[ERROR] [MY-010262] Can't start server: Bind on TCP/IP port. Do you already have another mysqld server running on port: 3306? → 端口被占，先 netstat -tlnp | grep 3306。
[Warning] [MY-010055] IP address '1.2.3.4' could not be resolved → 反查 DNS 超时，加 skip-name-resolve 能治，但改之前先确认权限表里用的是 IP 不是主机名。
[Note] [MY-010253] InnoDB: Buffer pool(s) load completed at ... → 正常启动信息，不用管（但 verbosity=1 时它就不写了）。

3. 二进制日志：唯一能重放历史的那本账

binlog 以事件（event）为单位记录「数据库发生了什么变化」。官方给它的用途只有两个：主从复制和时间点恢复。8.0 起默认开启，不用额外配。

3.1 记什么、不记什么

课程那句话要补一个例外

「不记录数据查询语句」是对的，但反过来要精确：语句「可能」改数据就会记。一条 DELETE FROM emp WHERE id = -1 一行没删，在 STATEMENT 格式下照样进 binlog（因为「可能」改）；换成 ROW 格式则不会，因为没有任何行镜像产生。
真正决定「记不记」的是有没有产生变更事件，不是「这条语句有没有跑成功」。

3.2 三个参数决定它在哪、叫什么

参数默认值（8.0）说明
log_binON只读。关它要加 skip-log-bin 重启，不能在运行中 SET
log_bin_basename/var/lib/mysql/binlog路径 + 前缀。8.0 默认前缀是 binlog，老版本是 host_name-bin
log_bin_index/var/lib/mysql/binlog.index文件清单。不要手工改，会把它改乱

3.4 清理与保留

binlog 会一直长。清理有三种办法，顺序是从细到粗，能指定范围就别用「全清」：

sql-- ① 先看有哪些、多大、当前写到哪个
SHOW BINARY LOGS;          -- 文件名 + 大小
SHOW MASTER STATUS;        -- 当前正在写的文件与位点

-- ② 删到某个文件之前（不含该文件本身）
PURGE BINARY LOGS TO 'binlog.000010';

-- ③ 删到某个时间之前
PURGE BINARY LOGS BEFORE '2026-11-01 00:00:00';

-- ④ 只切一个新文件，不删任何东西（备份前、改配置后常用）
FLUSH BINARY LOGS;

-- ⑤ 全清：删掉所有 binlog，编号回到 000001，同时清空 GTID 历史
RESET MASTER;                     -- 8.0.34 起弃用
RESET BINARY LOGS AND GTIDS;      -- 8.4 的写法，含义相同
shell# 自动过期：默认 30 天，改小到 7 天
mysql -uroot -p -e "SET PERSIST binlog_expire_logs_seconds = 604800"
mysql -uroot -p -e "SHOW VARIABLES LIKE 'binlog_expire%'"
# binlog_expire_logs_seconds   604800
# expire_logs_days             0        ← 已弃用，别再配这个
PURGE 不检查从库进度，这是最容易搞出事故的一步

PURGE BINARY LOGS 只问「这个文件还有没有在被写」，不问从库读没读完。主库上删掉的文件，从库的 IO 线程还要去拉，报 ERROR 1236 (HY000): Could not find first log file name in binary log index file，复制当场断。
正确顺序：先在每个从库执行 SHOW REPLICA STATUS\G，记下 Source_Log_File，只 PURGE 到那个文件之前；有从库已经停了很久，就别 PURGE，先修从库。
另外两个细节：RESET MASTER 在从库还在跑的时候行为是「未定义」的，官方明确不支持；自动过期也不是到点就删，只在启动和 flush 日志时才会真正清理。

保留多久才够

两条硬约束取大者：① 备份周期 × 2（每天备份就要留 48～72 小时，否则备份之间的窗口没法恢复）；② 从库最长可能的停机时间（从库挂 3 天，你就得留 3 天以上的 binlog，不然只能重建）。
这两条一算就知道「默认 30 天」对生产是够的，对磁盘小的小机器则太奢侈——按容量反推，别照抄。

4. 查询日志：唯一记「读」的账

查询日志记客户端发来的每一条语句，包括 SELECT，还包括连接与断开。它和 binlog 恰好互补：binlog 只有「变化」，查询日志只有「请求」。默认关闭。

sql-- 临时开，排完就关（不需要重启）
SET GLOBAL general_log = 'ON';
SET GLOBAL log_output = 'FILE';
SHOW VARIABLES LIKE 'general_log%';

-- 别忘了关
SET GLOBAL general_log = 'OFF';

-- 只想排除自己这个会话（比如你在里面查日志，别把自己的查询也记进去）
SET sql_log_off = ON;
用它的正确姿势：短开、带时间窗、用完就关

查询日志的价值是「还原客户端到底发了什么」——ORM 拼错表名、连接池把事务拆成两条、某个 SDK 偷偷发了一条全表扫。这类问题用别的手段都看不到。
但它不是监控手段：一个 500 QPS 的库，一天能写出几十 GB。真要长时间留，用 log_output=TABLE 加定期清理，或者干脆上审计插件（audit_log / general_log 的替代品），别拿它当常态。

5. 慢查询日志：判的是「两道条件」

慢查询日志的判定条件最容易记错。官方定义是同时满足两条：「执行时间 ≥ long_query_time」并且「扫描行数 ≥ min_examined_row_limit」。默认 long_query_time=10、min_examined_row_limit=0，日志默认关闭。

ini# /etc/my.cnf · [mysqld] 段
slow_query_log            = 1
slow_query_log_file       = /var/lib/mysql/slow.log
long_query_time           = 1          # 单位秒，可写 0.5
min_examined_row_limit    = 0

# 两个「扩大收集面」的开关，按需开
log_slow_admin_statements      = 1     # 慢 DDL 也记（默认关）
log_queries_not_using_indexes  = 1     # 没走索引的也记（默认关，易刷屏）

# 8.0.14+：多输出一批字段，定位更准
log_slow_extra            = ON
shell# 不改文件也能开：动态参数，立刻生效
mysql -uroot -p -e "SET GLOBAL slow_query_log=1; SET GLOBAL long_query_time=1"

# 验证到底开没开
mysql -uroot -p -e "SHOW VARIABLES LIKE 'slow_query%'"
mysql -uroot -p -e "SHOW VARIABLES LIKE 'long_query_time'"

# 汇总，而不是一条条翻：-s t 按总耗时排序，-t 10 取前 10
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log

慢日志的每条记录长这样，真正有用的是 Rows_examined 和 Rows_sent 的比值：

# Time: 2026-11-25T19:02:11.123456+08:00
# User@Host: root[root] @ localhost []  Id:  12
# Query_time: 12.345678  Lock_time: 0.000123  Rows_sent: 3  Rows_examined: 2000000
SET timestamp=1795604531;
SELECT * FROM emp WHERE name LIKE '%张%';
怎么读这一行

Rows_examined: 2000000 + Rows_sent: 3 = 扫了 200 万行只返回 3 行，典型的没走索引（LIKE '%张%' 前面带通配符，索引用不上）。
Query_time 里不含等锁的时间（官方明确：初始锁的获取时间不计入执行时间），所以「慢」和「卡在锁上」要看 Lock_time 或 performance_schema，别看这一个数就下结论。
另外 # Time 那行受 log_timestamps 影响，默认 UTC——和你系统时间差 8 小时，别以为记错了。

改了 long_query_time 却没生效：这是最经典的坑

long_query_time 是 global + session 两级变量。你在已连着的会话里 SET GLOBAL long_query_time = 1，当前连接仍是旧值（10 秒），只有新建立的连接才用 1 秒。
所以在同一个窗口里「设置完马上跑一条 0.5 秒的 SQL，没进慢日志」，不是功能坏了，是你没重连。验证要在新会话里做，或者干脆 SET SESSION long_query_time = 1; 给当前会话单独设。

参数默认值说明
slow_query_logOFF总开关，动态可改
slow_query_log_filehost_name-slow.log相对路径落在数据目录；建议改绝对路径并换盘
long_query_time10最小 0，精度到微秒；global 与 session 两级
min_examined_row_limit0扫描行数下限；调大会漏掉「快但扫全表」的小查询
log_slow_admin_statementsOFF慢 DDL 也记
log_queries_not_using_indexesOFF没走索引就记，不看耗时；开着极易刷屏
log_throttle_queries_not_using_indexes0每分钟最多记多少条未用索引的语句，0 = 不限
log_outputFILE与查询日志共用；TABLE 时写 mysql.slow_log

6. 出事了，先翻哪本

把上面四本账按「症状」重排一遍，才真正用得上：

症状先看具体动作
服务起不来 / 启动几秒就退出错误日志先拿到路径：mysql -e "SELECT @@log_error" -N -B（连不上就按装法猜），再 tail -n 200 该文件，往上翻找第一条 [ERROR]
连不上，报 2002 / 2003 / 1130错误日志先看端口是否在监听（ss -lntp | grep 3306），再看日志里有没有 Aborted connection
数据被误删 / 误改，要回滚二进制日志mysqlbinlog --start-datetime=… binlog.0000NN 定位，再按位点回放到临时库
主从断了 / 延迟越来越大二进制日志SHOW REPLICA STATUS\G 看 Last_IO_Error，对照主库 SHOW BINARY LOGS 判断是不是被 PURGE 了
某几条 SQL 偶发很慢慢查询日志mysqldumpslow -s t -t 10；重点看 Rows_examined / Rows_sent
「代码里明明没这句 SQL」查询日志短开 general_log，过滤出该连接（Connect 行有线程号）看它到底发了什么
磁盘突然满了二进制日志SHOW BINARY LOGS 看总量；du -sh /var/lib/mysql 对照；别第一反应删 binlog，先确认从库
要查「谁读了这张表」都不行binlog 不记 SELECT；查询日志默认关且不长期留。要么开审计插件，要么开查询日志短窗口抓，要么上数据库审计产品
一句话记法

「起不来」看错误日志，「改坏了」看 binlog，「慢」看慢日志，「没发过这句」看查询日志。四句话对应四个场景，排障时先认清场景，再决定翻哪本。

7. 与课程里的说法有出入的几处

课程录的是 8.0 早期环境，下面这几处按 8.0 现在的行为改过来了（也都标了版本）：

课程里的说法8.0 的实际行为
「上述所有参数配置完成后，都需要重启 MySQL 服务器才生效」 只有 log_bin、log_error 这类静态参数必须重启。general_log、slow_query_log、long_query_time、log_queries_not_using_indexes、binlog_expire_logs_seconds 都能 SET GLOBAL 立刻生效，SET PERSIST 还能同时写进配置、重启后保留
-o「忽略掉日志中的前 n 行命令」 跳的是前 N 个 事件（event），不是行。一个事件可能对应一大段输出，按「行」理解会算错
清理用 RESET MASTER、PURGE MASTER LOGS PURGE MASTER LOGS 是 PURGE BINARY LOGS 的旧名（还能用）；RESET MASTER 在 8.0.34 起标记弃用，8.4 换成 RESET BINARY LOGS AND GTIDS
错误日志默认 /var/log/mysqld.log 只有 RPM/YUM 安装是这样。Debian/Ubuntu 是 /var/log/mysql/error.log，源码编译是数据目录下 host_name.err。以 SELECT @@log_error 为准
binlog 默认保留 30 天，配 expire_logs_days 天数这个参数在 8.0.3 就弃用（8.2 已移除）。现在是 binlog_expire_logs_seconds=2592000，单位秒，可以配到精细
binlog_format 三种随便选 8.0 默认 ROW；8.0.34 起整个参数标记弃用，方向是只保留 ROW。新搭的库就别再纠结 STATEMENT 了
还有两个课程没提、但配置时一定会撞上的

log_timestamps：错误日志、查询日志、慢日志的文件里时间戳都用它，默认 UTC。所以你看到的时间比北京时间早 8 小时，不是日志坏了，改 SET PERSIST log_timestamps='SYSTEM' 就好。
FLUSH LOGS 与 FLUSH BINARY LOGS 不是一回事：前者刷所有日志（含错误日志、慢日志、binlog），后者只切 binlog。备份脚本里想切 binlog，用后者更精确。

自测三问先自己答一遍，再点开对答案

Q1你在当前会话里执行 SET GLOBAL long_query_time = 0.1，然后马上跑一条 0.5 秒的 SQL，慢日志里没有。功能坏了吗？

没坏。long_query_time 是 global + session 两级，SET GLOBAL 只改全局默认值，已经建立的连接继续用自己的旧值（10 秒）。要么断开重连，要么在当前会话补一条 SET SESSION long_query_time = 0.1;。

Q2主库磁盘告警，执行了 PURGE BINARY LOGS BEFORE NOW()，十分钟后从库复制中断，报 ERROR 1236。为什么？

PURGE 只看「文件还在不在被写」，不检查任何从库的读取进度。从库的 IO 线程还没读到就被删了，只能从备份重建。
正确做法：先在每个从库SHOW REPLICA STATUS\G 记下 Source_Log_File，只 PURGE 到那个文件之前；有从库长期停着，就别 PURGE。

Q3用 mysqlbinlog binlog.000003 只看到一堆 BINLOG 'xxx' 的 base64，看不到 SQL。怎么解？而回放时又该注意什么？

8.0 默认 binlog_format=ROW，行事件本来就不以 SQL 形式输出。看的时候加 -v --base64-output=DECODE-ROWS，才会把行变更重构成可读的伪 SQL。
回放时绝对不能带 -v：带 -v 输出的行变更全是 ### 开头的注释，喂给 mysql 会被当注释丢掉，看起来执行成功、数据一行没变。看和回放永远是两条命令。

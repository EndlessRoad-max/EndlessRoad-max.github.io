02-03网络与协议细节

复制是「一条长连接 + 一堆事件」。这一页回答三个问题：数据在哪一层流动、连接是怎么一步步建起来的、线路上到底跑的是什么。

环境：MySQL 8.0前置：02 主从复制 已搭通整理：2026-11-26

一屏速记合上笔记，这 4 条要能自己说出来

  1. 只有服务层在通信：从库不挂主库磁盘、不读数据文件，读 binlog 的是主库为它起的 Dump 线程。
  2. 从库发起，主库推送：起点是从库「拉」（我连上、我给坐标），之后是主库「推」（有新事务就发）。
  3. 传的是 binlog 事件，不是 SQL 文本；ROW 格式下一条 UPDATE 改 3 行就是 3 个行事件。
  4. 三种「完成」互不等价：TCP ACK、半同步 ACK、从库事务提交，一层比一层强。

1. 一条 INSERT 的全链路

贯穿全图的一句话：INSERT INTO db01.tb_user(name) VALUES ('Tom');。两台实例内部都分成服务层 / 存储引擎层 / 文件层，主从之间只有服务层在通信。

主库：先写，再发

InnoDB 改数据，提交时协调出 binlog 事件；Dump 线程读本机 binlog，按从库要的起点往后发。

从库：先收，再放

receiver 把事件写进 relay log 就结束了；applier 再读 relay log 执行，落在自己的 InnoDB 上。

为什么「三个线程」这个说法容易错

线程数不是一个固定值：主库上每个从库连接一个 Dump；从库上 receiver 一个、applier 可以有多个（并行复制时是 coordinator + N 个 worker）。所以「一主一从三个线程」只在最简配置、串行应用时成立。

2. 连接的八个回合

从库用一个临时端口连主库 3306，先走 MySQL 握手与账号认证（选了 TLS 的话，TLS 握手插在认证之前，之后所有协议数据都在加密通道里），再用 COM_BINLOG_DUMP 说明「从哪个文件、哪个位置、我是哪个 server_id」。主库随后在这条连接上连续发事件。

「拉」和「推」说的是两个阶段

起点是从库拉：我连上来、我指定从哪开始。之后是主库推：有新事务就发，没有就等着。所以既不是从库每秒来查一次，也不是主库主动去连从库。

3. 线路上跑的是事件

传的是 binlog 事件。ROW 格式下 DML 记的是行变更，CREATE TABLE 这类 DDL 仍然可以是一条语句事件；一个事件里可以装多行变更——别把「改了几行」和「产生几个事件」画等号。

4. 三种「完成」

看到哪种「完成」它能说明什么
TCP ACK对端网卡收到了这些字节。仅此而已，不代表刷盘，更不代表事务已应用。
半同步 ACK从库确认事件已写入并刷到 relay log。仍然不代表表里的数据已经改完；普通异步复制根本不等待这个确认。
从库事务提交本机数据变了，新开的查询才看得到。已开启的旧快照事务仍可能读到旧值。

5. 断开之后

断点续传靠「文件名 + 位置」这一对坐标：receiver 重连、重新认证，然后从记录的进度继续请求，已保留的 relay log 可以接着补。

不同文件里的 position 不能互相比较。如果主库已经把所需的 binlog 清掉，只能拿备份重新初始化——不能把起点改成最新位置来掩盖缺口，那样丢的数据永远不会回来。

重连不是无限的

8.0 有 SOURCE_RETRY_COUNT（默认 86400 次）和 SOURCE_CONNECT_RETRY（默认 60 秒）。日志文件被清理这类错误，会一直重试到次数耗尽，然后 Replica_IO_Running 变成 No。

6. 容易记错的地方

四处，逐条对照
  • Seconds_Behind_Source = 0 不证明追平；8.0 里接收停了、relay log 也应用完时，这个值可能是 NULL。
  • Auto_Position = 0 只说明这是位点复制，不是「位点一变就断」。
  • 无主键表在 ROW 下不一定全表扫，也可能走其他索引；但定位成本高，容易拖慢应用，先看证据再改。
  • RESET REPLICA ALL 清的是复制通道和日志，它不是防双写的手段；旧主还能写才是双写的根源。

自测三问先自己答，再展开对照

Q1从库的 receiver 是怎么读到主库磁盘上的 binlog 的？

它读不到。receiver 在协议上只是个普通客户端，发 COM_BINLOG_DUMP 说明起点；真正读文件的是主库为这个连接启动的 Binlog Dump 线程，读出来再通过同一条 TCP 连接发给它。

Q2一条 UPDATE 改了 500 行，网络上传的是什么？

ROW 格式下传的是行变更事件：一个 TABLE_MAP 加一批 UPDATE_ROWS（500 行可能分装在多个事件里），最后 XID 收尾。
不是那条 UPDATE 语句——SQL 文本只在 STATEMENT 格式下才传。

Q3开了半同步，主库返回「成功」时，从库的表一定改好了吗？

不一定。半同步确认的是「事件已写入并刷到 relay log」，applier 可能还没应用。
而且超时会退回异步——那时连这个确认都没有，所以要监控回退，别假设它一直生效。

02-01GTID 复制

位点复制的痛点是「换一台主库，位点就作废」。GTID 给每个事务发一个全局编号，从库只认「哪些事务我执行过」，换源不用再找文件名和位置。

环境：MySQL 8.0.32+前置：02 主从复制 已搭通整理：2026-11-26

一屏速记合上笔记，这 4 条要能自己说出来

  1. 编号：GTID = 来源 server_uuid : 事务序号。级联转发时保留原来的来源，所以一台实例的已执行集合里可能有多个 UUID。
  2. 作用：换源后靠集合自动对齐、已执行的自动跳过。不改变异步确认方式，不保证数据必然一致，也不会自己切主库。
  3. 写法：SOURCE_AUTO_POSITION=1 与 SOURCE_LOG_FILE/POS 互斥，用 GTID 就只写前者。
  4. 前提：从库接得上，靠的是主库还留着它缺的那段 binlog；历史日志被清掉，照样得用备份重建。

1. GTID 是什么

开 GTID 后，主库每提交一个事务就给它一个编号：uuid-a:108。从库记住「我执行过哪些编号」，重连时把自己缺的部分告诉主库，主库只发这些。

它替掉了位点复制里最烦的一件事：主库换了、日志轮转了、路径变了，位点全作废。改成集合之后，从库只要说清自己有什么，剩下的主库来补。

2. 全新环境怎么开

只适用于两台全新的练习实例

下面的做法是「一开始就开着 GTID」。不要把正文里已经在跑的 gtid_mode=OFF 环境直接 SET 成 ON——在线转换是分阶段的流程，见第 5 节。

  1. 两边都写进配置主库 · 配置文件 
    [mysqld]
server-id = 1
log-bin = binlog
binlog-format = ROW
gtid-mode = ON
enforce-gtid-consistency = ON
log-replica-updates = ON
    从库 · 配置文件 
    [mysqld]
server-id = 2
log-bin = binlog
binlog-format = ROW
gtid-mode = ON
enforce-gtid-consistency = ON
log-replica-updates = ON
relay-log = relay-bin
read-only = ON
super-read-only = ON

    server-id 两台必须不同；enforce-gtid-consistency 是 gtid-mode=ON 的前提，两项一起开。

  2. 重启后核对两台 · mysql 客户端 
    SELECT @@server_id, @@server_uuid,
       @@gtid_mode, @@enforce_gtid_consistency,
       @@log_bin, @@log_replica_updates;

    期望 ON / ON / 1 / 1，两个 server_uuid 不同。之后建复制账号、测 TLS 连通，完全照02 主页「主库第 3 步」做，账号与密码规则一样。

  3. 用 AUTO_POSITION 指源从库 · mysql 客户端 
    CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '192.168.200.200',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = 'ReplaceWithYourReplPassword!',
  SOURCE_AUTO_POSITION = 1,
  SOURCE_SSL = 1;

START REPLICA;
SHOW REPLICA STATUS\G

    不写 SOURCE_LOG_FILE 和 SOURCE_LOG_POS——给了位点就不是自动定位了，两者互斥。

    看 Auto_Position: 1、两个 Running 为 Yes、Retrieved_Gtid_Set 开始出现 UUID 区间。再按正文第 6 步写一条 INSERT，在从库查得到才算通。

3. 主库已有数据，怎么初始化

前提：主库已开 GTID 且在跑业务；从库是全新的、没有业务写入、没有 GTID 历史；工具用 8.0.32+。已有 GTID 冲突的从库不能靠清空掩盖，只能重建。

  1. 导出：这次要带 GTID 集合主库 · Linux 终端 
    mysqldump -u root -p \
  --single-transaction --source-data=2 \
  --set-gtid-purged=ON \
  --routines --events --triggers \
  --databases db01 \
  --result-file=/tmp/gtid-seed.sql

grep -m 2 -E '^SET @@GLOBAL.gtid_purged|^-- CHANGE (REPLICATION SOURCE|MASTER)' /tmp/gtid-seed.sql

    --set-gtid-purged=ON 会把源库的已执行集合写进备份（SET @@GLOBAL.gtid_purged），从库导入后就拥有了「这些事务我做过」的账。位点模式下这里写 OFF，GTID 模式下写 ON——同一个参数，两种场景取值相反。

    能 grep 到 gtid_purged 与坐标注释两行。注意：即使只导 db01，写进去的集合仍然包含源库所有已执行事务。所以要复制的业务库必须一次导全，不能漏库还声称完整；系统账号另行管理。

  2. 导入：临时放开只读从库 · mysql 客户端（管理员） 
    SET GLOBAL super_read_only = OFF;
SET GLOBAL read_only = OFF;
SOURCE /tmp/gtid-seed.sql;
SET GLOBAL super_read_only = ON;
SHOW REPLICA STATUS\G

    备份脚本自己会处理 sql_log_bin 和 gtid_purged，不用手动加。导入过程不能报错；有错就先修，别急着启动复制。新的从库没有冲突 GTID，这一步才是安全的。

    SELECT @@GLOBAL.gtid_executed; 此时应当已经包含备份里那段集合。

  3. 启动后先看集合，再看数据

    连接参数与第 2 节第 3 步完全一样：SOURCE_AUTO_POSITION=1，不写位点。START REPLICA 之后，从库会从集合的缺口处向主库要日志。

    主库必须保留缺口那一段 binlog，直到从库收完。日志已被清理时，只能重新取基线。

4. 怎么确认追上了

「两个 Yes」只说明线程活着。要判断数据到没到，用一个集合去等：

-- 主库：记下这一刻的集合
SELECT @@GLOBAL.gtid_executed;

-- 从库：最多等 30 秒，看这个集合是否已执行完
SELECT WAIT_FOR_EXECUTED_GTID_SET('uuid-a:1-110', 30);

返回 0 表示这批事务都执行过了；返回 1 表示等超时，还没追上。

「执行过」不等于「逐行校验过」

复制过滤、跳过的事务、绕过 binlog 的手工写入，都可能让两边的数据不一样。要证明一致，得另做校验（checksum、逐表比对）。

状态里还有两个集合：Retrieved_Gtid_Set 是收到哪些，Executed_Gtid_Set 是执行了哪些。不要要求前者包含后者——从库自己本地产生的事务、以及其他来源的事务，也会出现在已执行集合里。

5. 它不解决什么

不改变确认时机

GTID 仍然是异步复制，主库提交完就返回，不等副本。

不保证数据一致

它只保证「不重复执行」，不保证内容逐行相同。

不会自己切主库

判断、隔离、提升、改路由，是故障管理的事。

不能替代日志保留

主库把缺口那段删了，GTID 也补不回来。

已经在跑 OFF 的环境要转 ON，是分阶段流程（OFF → OFF_PERMISSIVE → ON_PERMISSIVE → ON，并且先开 enforce_gtid_consistency），不能一条 SET 完事。具体步骤以官方文档为准：在线启用 GTID。本页不提供「照着抄就能上生产」的转换清单。

自测三问先自己答，再展开对照

Q1从库 Executed_Gtid_Set 里出现了两个不同 UUID，正常吗？

正常。事务跨级联转发时保留原来源的 GTID，所以一台实例的集合里会有多个 UUID 区间：一部分来自老主库，一部分来自现任主库，还可能有它自己本地执行的事务。

Q2为什么 GTID 建从库时 --set-gtid-purged 要写 ON，而搬到别的实例却写 OFF？

建从库要让新实例知道「这些事务在源上已经做过了」，否则重放会重复。ON 把集合写进备份，导入后就有了账。
搬到另一个独立实例（不参与复制）时写集合反而会让它拒绝执行、或污染它的执行历史，所以用 OFF。

Q3WAIT_FOR_EXECUTED_GTID_SET 返回 0，能说明两边数据完全一致吗？

不能。它只证明这批事务在从库执行过。复制过滤、手工跳过、绕过 binlog 的写入，都会让数据出现差异。要一致就得单独做校验。

## 一、先分清五类任务

论文把表格数据整理分为纠错、插补、归一化、集成和解释。前三类主要改善数据质量，后两类帮助连接数据、补充语义。这是按用途分类，不是必须依次完成的五个步骤。

### 1. 基本概念

论文用 `T = (A, V)` 表示一张表：`A` 是列属性的集合，`V` 是数据单元格值的集合。`v_ji` 表示第 j 行、第 i 列的值；值可以是文字、数字、日期等，并不只指数值。

- 表头说明这一列存的是什么，例如“姓名”“出生日期”。
- 列是同一属性下的一组值，行是一条记录。
- 模式（Schema）描述表的结构，包括列名、数据类型和约束。论文在多数讨论中将它简化为属性集合 `A`。

### 2. 五类任务的区别

| 任务 | 要解决的问题 | 简单例子 |
| --- | --- | --- |
| 纠错（TC） | 找出并修复错误值 | 把 `cicago` 改为 `Chicago` |
| 插补（TIp） | 为缺失值作出预测 | 根据相关记录补全缺失日期 |
| 归一化（TN） | 统一同义表达、格式和单位 | 将不同日期写法统一为 `YYYY-MM-DD` |
| 集成（TInt） | 找到不同数据来源之间的对应关系 | 判断两张客户表中的记录是否指向同一个人 |
| 解释（TItp） | 识别单元格、列及列间关系的含义 | 判断某列是“人名”，两列之间是“出生于”关系 |

纠错通常分为“检测错误”和“修复数据”。除了拼写错误，还包括无效日期、跨表冲突、违反业务规则等情况。例如，离职日期早于入职日期就可能是错误。不过，两张表的价格不同，也可能是时间或统计口径不同，需要结合上下文判断。

插补得到的是预测值，不一定是原始事实。整理实际数据时，应区分“确实漏填”“不适用”“未知”等情况，不能见到空白就补值。

归一化有两个子任务：

- 语义规范化（SC）：把指向同一实体或含义相近的表达归到一起，如在语境明确时归并 `Trump` 与 `Donald Trump`。
- 语法转换（ST）：统一日期、单位、大小写等表达格式。

这里的 Normalization 指值和表达的规范化，不是数据库的第一、第二、第三范式，也不专指把数值缩放到 0～1。

集成的范围比“匹配后拼表”更广。数据元素之间可以存在等价、包含、重叠或互斥关系。论文重点讨论其中的等价匹配，即 Table Matching：

- 实体匹配（EM）：判断两条记录是不是同一个现实实体。
- 模式匹配（SM）：判断两列是否表达相同属性，如 `sex` 与 `Gender`。

### 3. 表格解释具体标注什么

表格解释也叫语义表格标注。它可以借助外部知识库或本体，为表格元素补充机器可读的含义。

| 子任务 | 标注对象 | 输出含义 |
| --- | --- | --- |
| 单元格实体标注（CEA） | 单个单元格 | 这个名字对应知识库中的哪个实体 |
| 记录实体链接（REL） | 整行记录 | 这条记录描述的是哪个实体 |
| 列类型标注（CTA） | 一列 | 这一列是人名、国家、日期等哪种类型 |
| 列属性标注（CPA） | 两列 | 两列之间是出生日期、国籍等哪种关系 |

CEA 的前提是知识库中存在合适的实体，不能强行给每个值找一个链接。CPA 还要区分关系方向，例如“人物—出生日期”中，人物列是主语，日期列是宾语。

论文指出，已有文献经常混用 CEA 和 REL，综述也合并讨论了它们。但理解概念时，仍应区分“一个单元格”和“一整行”。

### 1. 各类任务的常见做法

纠错主要依赖规则、外部参考数据和学习模型。例如，按业务约束检查不合理的日期，用标准地址库核对地址，或从数据中学习哪些值更可能出错。主动学习等方法可以减少人工标注量。

插补可以用已有完整记录训练预测模型，也可以利用矩阵分解估计缺失值。另一类方法学习数据分布，再生成缺失部分，包括去噪自编码器、GAN、VAE 和扩散模型。

归一化中的语义规范化，通常借助知识库链接或聚类，把相同或相近的表达归在一起。格式转换则可以根据用户提供的输入输出示例生成程序，即 Transform-by-Example（TBE）；也可以根据模式生成转换程序，即 Transform-by-Pattern（TBP）。USTL 还会把转换逻辑相似的值对聚类处理。

实体匹配通常先筛选候选，再精细判断。前一步称为分块（Blocking），用于减少需要逐一比较的记录对。模式匹配则可以看列名和类型，也可以看列中的实际数据，或者同时使用两类信息。

表格解释主要有两条路线：一是从预设标签中预测类型，二是与知识库中的候选实体或概念进行匹配。Sherlock、TURL、Doduo 等是论文提到的相关代表方法。

### 2. 传统方法的局限

论文主要指出三类问题：迁移到新领域后效果可能下降；错误、缺失和不规范表达会影响特征提取；不同任务往往需要单独设计规则、特征或模型。

这些问题不意味着传统方法“换表就失效”。在规则明确、数据分布稳定的场景下，它们仍可能更便宜、更容易验证，也更适合重复执行。

### 3. 数据整理与表格理解有什么关系

两者的侧重点不同。数据整理关注数据是否准确、完整、一致，以及是否便于后续使用；表格理解与推理关注如何理解表格内容，并完成问答、事实核查、计算等任务。

两者有重叠，也会相互借用技术。检查一条跨表业务规则，本身就需要理解和推理能力。因此，不宜把它们理解成“先彻底洗干净，再开始理解”的固定顺序。

论文提到的相关方法包括 TAPAS、TAPEX，以及 Dater、Chain-of-Table、Tree-of-Table、HyperG、OpenTab、PoTable 等。可以重点理解其中的思路：拆分问题、检索相关表格、分步操作表格，以及先规划再执行。

注意，Chain-of-Table 与 Chain-of-Thought 名称接近，但不是同一种方法；使用缩写时应写清楚。

1. 数据来源集中于网页和维基百科，医疗、金融、工业等领域的覆盖不够。
2. 合成或增强数据可能与真实错误分布不同，尤其难覆盖少见但复杂的错误。
3. 缺少对多步、跨表整理流程的整体评测。

对实际项目来说，只测某一步的准确率还不够。例如，插补后的值是否让后续分析更可靠，修复一张表后是否破坏了另一张表的约束，也需要检查。

## 四、大模型处理表格的四类关键技术

论文归纳了过滤、序列化、提示词工程和模型增强四个模块。这是一个分析框架，不代表每种方法都必须按固定顺序执行四步。尤其是训练，通常发生在模型使用前，而不是每次处理表格时都重新训练。

Fig. 3 用补全 Hemingway 的生日说明这些模块：选取相关行，把表格转成文本，加入任务指令和参考信息，再由模型给出答案。图中的输出是示例，不是准确性保证。

### 1. 过滤：只保留当前任务需要的内容

大表转成文本后可能很长。无关内容既增加成本，也可能干扰模型使用关键证据。过滤就是从原表或参考表中选取相关行、列或单元格。

例如，只补一个人的生日时，可以保留这个人的记录、能够确认其身份的字段，以及相关参考记录。GPT4Table 使用预设长度约束，另一些方法则按任务相关性筛选内容。

筛选也有代价：删得过多可能丢掉消歧所需的信息。因此，目标是减少无关内容，同时保留足够证据，而不只是把输入压得越短越好。

### 2. 序列化：把二维表转成模型可读的输入

对于文本输入的模型，需要把表转换成线性文本，并尽量保留行列对应关系。

Table III 共列出 15 种方法。为便于记忆，这里按表达形式分组；这不是论文另设的分类体系。

- 分隔或位置标记：Markdown、Vanilla-T、Row-Identifier、Column-Identifier、X-Separated。后者包括 CSV、TSV 等分隔形式。
- 标签与排版：HTML、LaTeX。
- 键值或数据结构：Attr-Value Pairs、Data Matrix、DFLoader、Row-JSON、Tree-JSON。Tree-JSON 用树结构表示层级、位置和单元格内容。
- 值序列或自然语言：Values-only、Row_sentence、Column_sentence。其中 Values-only 只顺序列出值，本身不是自然语言句子。

论文引用的研究发现，Markdown、JSON、HTML 等结构化表示在若干任务中优于较松散的文本表示；DFLoader 和 JSON 在事实查找、数据转换中表现较好，HTML 或 XML 在一些问答和事实核查实验中更有优势。

这些结果来自不同任务和实验设置，不能概括为某种格式始终最好。选择格式时，要考虑表结构、任务和模型，并用自己的数据验证。

### 3. 提示词：说清楚任务、表格和输出要求

Table-GPT 使用 `(Instruction, Table, Completion)` 结构，把任务指令、表格内容和输出区分开。这里的 Completion 是模型生成的答案，或训练样本中的目标答案，不是推理时需要提前提供的正确答案。

常见的增强方式有三种：

- 少样本上下文学习：给出几个任务示例。示例是否相关、顺序如何、是否足够多样，都可能影响结果。
- 检索增强生成（RAG）：从知识库、数据湖等来源找参考信息，再交给模型处理。它能补充知识，但效果取决于检索结果的质量。
- 推理增强提示：引导模型分步处理问题。步骤更详细并不自动意味着答案更正确，仍需验证结果。

### 4. 模型增强：改进工作流程，或训练模型

表格既有行内联系，也有列内联系，还混合了文本、数字、类别和缺失值。业务约束经常没有直接写在表里，这些都增加了处理难度。

免训练策略不更新模型参数，主要通过安排工作流程发挥模型能力。论文归纳了五种角色：

| 角色 | 主要职责 |
| --- | --- |
| Solver | 直接给出任务结果 |
| Expert | 提供背景知识、规则或解释 |
| Coder | 生成 Python、SQL 等代码，由工具执行 |
| Checker | 检查结果是否正确或一致 |
| Agent | 协调工具、模块和用户交互，完成多步任务 |

图中的 Expert-Solver、Solver-Checker 是角色的组合方式。同一个基础模型也可以通过不同调用承担不同角色，不一定要部署多个不同模型。

Coder 的好处是转换逻辑可以复用和检查，也适合批量执行。但生成的代码仍可能写错、漏处理边界情况或误改数据，不能把它理解为“零幻觉”。Checker 也可能漏检，不能仅凭另一个模型认可就断言结果正确。

基于训练的策略主要包括：

- 持续预训练（CPT）：继续使用表格相关语料训练模型，例如 GTL、TableGPT2。
- 监督微调（SFT）：使用带目标答案的任务数据训练。数据既可以由人工标注，也可以由更强的模型生成，其中可能包含解释或推理步骤。

LoRA、LongLoRA、T-Few 等用于降低或调整微调成本。知识蒸馏可以为小模型提供训练数据，但生成数据本身也需要质量控制。

### 1. 纠错：发现问题之后，还要检查修复是否合理

作为 Expert，模型可以帮助提取或检查规则。LLMClean [152] 从原始数据推导上下文模型，使用传感器能力依赖、设备连接依赖等知识检测错误。Cocoon [150] 则检查统计上较强的函数依赖是否符合实际语义。

作为 Solver，模型直接检测并提出修复建议。Cocoon 会把拼写错误映射为正确值，再用 SQL `CASE WHEN` 批量处理；IterClean [148] 把工作分成检测和修复，并给出错误解释。

为了补充模型不知道的事实，RetClean [149] 从用户数据湖中检索相关记录，UniDM [67] 则先定位外部参考数据，再据此纠错。

IterClean 还在检测与修复之间加入核验模型，检查报错理由是否与上下文一致。多轮检查有助于减少误修，但“模型不再报告错误”不等于数据已经完全正确。

AutoDCWorkflow [147] 进一步使用 Agent，根据下游分析目标生成可执行的 OpenRefine 操作流程。

这类方法的难点是：修复事实性错误需要可靠依据，而检索结果和模型自己的判断都可能出错。

### 2. 插补：上下文、示例选择和成本都很重要

模型既可以辅助传统插补方法，也可以直接预测缺失值。

- MonotonicLR [136] 利用模型推断列间关系，辅助后续处理；CLAIM [137] 生成上下文描述，并使用带上下文的数据微调模型。
- Ji 等人 [134] 使用模型生成相关问题，辅助选择示例；Pool-search [133] 根据相似度动态检索示例；UniDM [67] 整理输入上下文，使其更容易理解。
- FS [74] 使用特征选择；Akella 等人 [75] 用强化学习选择并排列相关列，以减少输入成本。
- LLM-Forest [135] 组合多个少样本预测器，用置信度加权投票汇总结果。这里的多个预测器不一定是多个独立训练的基础模型。

插补的关键不只是“能否填出一个值”，还包括依据是否充分、缺失原因是什么，以及预测值会不会影响后续分析。

### 3. 归一化：区分语义归并和格式转换

语义规范化需要判断两个表达在当前语境下是不是同一个意思。

EDC [62] 先生成实体或关系的定义，再检索候选并判断能否归并。Few-shot clustering [113] 先用传统聚类，再让模型处理不确定的情况。Probing [114] 考察模型内部表示对科学同义词聚类的帮助。WDC-PAVE [112] 和 AutoAlign [59] 则使用候选集合等上下文辅助选择。

格式转换可以让模型直接输出结果，也可以生成代码。Narayan 等人 [72]、Brinkmann 等人 [112] 的实验说明，示例可能改善转换效果，但改善程度随模型而变。UniDM [67] 使用带占位符的填空式提示，IDSM+TRGM [109] 面向传感器数据转换。

生成代码的代表方法包括：

- SQLMorpher [108]：结合缺陷检测和表结构提示，迭代生成 SQL。
- DATAMORPHER [110]：分析表格特征，利用历史示例和特征选择辅助代码生成。
- NormTab [107]：先找出需要归一化的列，再针对这些列处理。
- FSTO-Gen [37]：生成功能语义类型，以及配套的归一化、校验和类型转换代码。

CleanAgent [106] 将对话管理、列类型标注、Python 代码生成和代码执行连成一个流程，帮助用户通过自然语言完成转换。

### 4. 集成：先缩小候选范围，再判断对应关系

Matcher 和 Selector 都属于 Solver，区别在于提问方式：前者判断一对记录是否相同，后者从候选列表中选出对应项。

逐对比较的成本会随数据量快速增长。对同一集合的 n 条记录去重，穷举需要 `n(n−1)/2` 次比较；两张分别有 m、n 条记录的表，穷举则需要 `m×n` 次比较。改成候选选择可以减少模型调用，但不能仅凭提示形式就断言消除了平方级成本，候选检索本身也有成本。

COMEM [58] 比较了 Match、Select 和 Compare 策略，发现候选选择在其细粒度识别实验中通常更有成本优势，先过滤再识别也有帮助。GRAM [61] 使用层级分类逐步缩小模式匹配的候选范围。

其他方法从不同环节降低成本或补充信息：BatChER [66] 批量处理记录对，Li 等人 [68] 选择信息量较高的记录对进行核验，KCMF [70] 引入伪代码分解和数据集知识，KG-RAG4SM [69] 检索知识图谱子图辅助匹配。

Wadhwa [64] 和 Steiner [65] 将大模型生成的解释用于训练小模型。综述也提到，微调可能削弱跨领域迁移能力，因此不能只看原数据集上的提升。

Peeters 等人 [63] 的实验还说明，显式匹配规则不一定有帮助：加入规则后，GPT-4 的表现下降，而部分开源模型有所提升。这是特定实验中的观察，不能简单解释为“规则限制了强模型”。

Harmonia [60] 和 Dango [239] 更关注实际工作流程，支持用户交互、工具调用和多表处理。Dango 还展示数据来源和处理依赖。综述强调，这类系统仍需要用户指导和结果验证。

### 5. 解释：结合表内信息、周边文字和外部知识

Oshima 等人 [42] 提取正文、表题、脚注等表格周边信息，再用模型补充背景、澄清指代。Self-Refinement [31] 根据验证反馈调整术语定义。

直接标注时，输入上下文的范围很重要。Korini 等人 [32] 比较了不同提示形式，其实验中表格级提示优于其他形式；ArcheType [36] 比较并动态选择序列化方式。这不意味着无论多大的表都应该完整输入。

CHORUS [34] 通过多轮对话处理相互关联的解释任务，例如先识别列类型，再判断列关系。它还设置锚定机制，在发现关键不一致时停止对话，减少早期错误向后传播。

RACOON [38] 从知识图谱中检索实体标签和一跳邻居，整理后放入提示。GenSTI [30] 则将解释任务转成代码生成形式，联合处理标注目标识别与语义标注；这里的“目标识别”不宜直接理解成计算机视觉中的目标检测。

## 六、怎样理解大模型与传统方法的比较

论文在这一比较中，把参数量超过 10 亿的模型称为 LLM。这是本文的讨论口径，不是统一的行业定义。LLM-Free 同时包括规则、统计方法和较小的学习模型，不能全部简化成“小模型”。

论文认为，大模型的主要优势是：可以通过自然语言接口处理多类任务，减少对专门标注数据的依赖，并利用预训练知识处理一些未见过的表达和实体。优势的程度仍取决于任务和数据。

作者据此提出，传统算法与大模型可以结合使用：让传统方法处理规则清楚、重复量大的部分，让模型补充语义判断，或检查不确定的候选。进一步的研究方向是让两者通过反馈或联合训练更紧密地协作。

## 七、论文提出的八个研究方向

以下是论文第 VII 节提出的方向，不表示这些问题已经得到解决。

1. 领域知识。医疗、金融、工业表格中的术语和约束可能超出通用模型知识。领域训练可能带来遗忘风险，RAG 则依赖检索质量。
2. 数值推理。模型对数字的表示和计算仍可能出错。论文建议研究更合适的数字表示、符号与神经方法结合，以及外部计算工具。
3. 类别值理解。同一个 `1` 在不同列里可能代表“是”、某个类别或其他含义，需要结合字段定义和上下文判断。
4. Agent 工作流程。将规划、执行、核验和迭代连接起来，处理步骤之间的依赖。这里不要求一定使用多个智能体。
5. 多模态处理。颜色、对齐、表头和版面可能携带信息，单纯转成文本会丢失其中一部分。
6. 输入长度。压缩和筛选表格时，需要兼顾成本、结构和必要的全局信息。
7. 跨表推理。处理多张表之间的关系、约束和错误传播，而不仅是孤立地清洗单表。
8. 计算成本。在更大规模的数据上，研究轻量模型、有效提示和混合处理流程，平衡效果与费用。

## 八、对 Excel 知识提取的启发

这一节是结合研究方向作的理解，不是论文已经实现的一套 Excel 处理方案。

对于从 Excel 构建知识图谱，表格解释最直接相关：CTA 帮助识别列的语义类型，CPA 帮助识别列之间的关系，CEA 和 REL 帮助把具体值或记录链接到已有实体。

不过，解释表格与构建新知识图谱仍有区别。表格解释可以使用已有知识库作为参照；如果要新建图谱，就需要另外考虑类型和关系如何定义，以及具体实体、属性、关系如何抽取和写入。不能把尚未构建的目标图谱当作已经可用的前提。

实际 Excel 文件还可能存在合并单元格、多行表头、注释、单位、多个表区和公式。应先识别这些结构，再判断一行、一列或一个值的含义。这篇综述主要提供数据整理与语义处理的方法框架，不能直接当作复杂 Excel 结构解析的完整解决方案。

继续阅读这些方法时，可以追问：它需要什么输入，依赖什么外部知识，输出能否验证，以及前一步的错误会怎样影响下一步。这比只记录它使用了哪个大模型更有帮助。
